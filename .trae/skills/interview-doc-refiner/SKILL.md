# 面试文档精炼器 (Interview Doc Refiner)

将面试录音原始记录整理为**深度结构化面试文档**的技能。以资深架构师面试官视角，结合候选人的项目资料、设计文档、个人简历，输出符合企业级 Agent 开发/架构师岗位标准的高分面试问答。

## 核心原则

1. **深度优先**：淘汰浅层问题，每个问题必须体现架构师级别的思考深度
2. **角色锚定**：始终以"企业级 Agent 开发/架构师"面试角色出发，不偏离该定位
3. **材料驱动**：回答必须基于候选人实际项目经历，引用具体技术细节（架构图、数据流、配置参数、故障案例）
4. **结构统一**：每个回答按 `理论定义 → 项目落地细节 → 解决的业务价值` 三段式结构组织
5. **适度扩展**：可补充企业级治理、工程化实践等加分内容，但不得编造候选人没有的项目经验

## 工作流程

### 第一步：材料收集与输入分析

读取以下输入材料：

| 材料类型 | 内容 | 用途 |
|---------|------|------|
| 录音原始记录 | 面试问答的初稿/草稿 | 问题来源、候选人口述内容 |
| 个人简历 | 工作经历、项目列表、技能 | 验证问题与经历的匹配度 |
| 项目设计文档 | 详细设计、架构文档、概要设计 | 提取具体技术细节注入回答 |
| 备考资料 | 八股文/面试题库 | 参考标准答案结构、补充理论深度 |

### 第二步：问题分析与重构

1. **剔除过浅问题**：删除"是什么"级别的基础概念问题（如"什么是 Agent"），保留或升级为"为什么这样设计"、"对比选型"、"落地踩坑"类问题
2. **合并同类问题**：将多个相关子问题合并为一个深度问题
3. **补充缺失维度**：检查是否覆盖以下核心模块：
   - Agent 核心编排（ReAct / Plan-Execute / Reflexion）
   - RAG 检索增强（分块策略 / 混合检索 / 重排 / Citation）
   - 工具调用与治理（MCP / Tool Gateway / 风险分级）
   - 记忆系统（滑动窗口 / 摘要压缩 / 长期记忆）
   - 多智能体协作（分层 / 对等 / 流水线）
   - 工程化实践（熔断器 / 模型路由 / 可观测性 / SSE 流式）
   - 企业级安全治理（RBAC / 审计 / Prompt 注入防护）
   - 差异化加分项（TEE / 隐私计算 / 联邦学习）
4. **调整问题角度**：将问题从"你做了什么"升级为"你为什么这样设计"、"对比方案是什么"、"如果遇到 XX 你怎么处理"

### 第三步：回答精炼

每个回答按以下模板组织：

**理论定义**（1-2 句核心概念，展现理论功底）
- 引用业界通用术语（ReAct、Plan-Execute、MCP 等）
- 给出对比视角（与替代方案的差异）

**项目落地细节**（3-5 句具体技术实现，展现工程能力）
- 引用设计文档中的具体配置、参数、架构图
- 包含选型对比表格、数据流描述
- 提及踩坑经历和解决方案（如：会话状态覆盖 → Redis Key 加租户前缀）
- 给出具体数据（如：MaxStep=25、滑动窗口 6 条、TTL 7d）

**解决的业务价值**（1-2 句总结，展现架构思维）
- 说明该设计解决了什么业务问题
- 量化效果（如：召回率提升 20%、人工介入率下降、故障定位效率提升）

### 第四步：结构化输出

文档结构模板：

```markdown
# 面试岗位 - 面试问答整理（深度修订版）

> **面试岗位**：XXX  
> **修订说明**：以资深 XXX 架构师视角，结合项目详细设计、企业级工程实践，按照"理论定义 + 项目落地细节 + 解决的业务价值"结构重构。

---

## 一、自我介绍相关

### Q1：XXX

**核心回答点（结构化呈现）**

1. ...

---

## 二、Agent 核心编排与架构设计

### Q2：XXX

**核心回答点**

**理论定义**：...

**项目落地细节**：...

**业务价值**：...

---

## 三、RAG 检索增强生成

...

## 四、Tool Gateway 与工具调用治理

...

## 五、系统并发、性能与工程化实践

...

## 六、企业级 Agent 安全治理

...

## 七、差异化加分项

...

## 八、总结：个人核心优势

1. ...
2. ...
3. ...

```

### 第五步：质量检查清单

输出前逐项检查：

- [ ] 问题是否覆盖了 Agent 核心编排、RAG、工具调用、工程化、安全治理等核心模块？
- [ ] 每个回答是否都引用了候选人的具体项目细节？
- [ ] 是否有对比表格或架构图文字描述来增强说服力？
- [ ] 是否包含了落地踩坑经验（而非只有理论成功案例）？
- [ ] 回答是否按照"理论定义 → 落地细节 → 业务价值"三段式结构？
- [ ] 是否有企业级治理视角的内容（多租户、RBAC、审计、熔断等）？
- [ ] 总结部分是否突出了候选人的差异化优势？
- [ ] 是否保持了"企业级 Agent 开发/架构师"面试角色定位，没有偏离？

## 示例

### 输入（录音原始记录）

```
Q：Agent 选型为什么用 Eino？
A：因为团队用 Go 开发，Eino 是 Go 的框架，字节开源的，就用它了。
```

### 输出（精炼后）

**核心回答点**

**选型对比**：

| 维度 | LangChain/LangGraph | 自研状态机 | Eino |
|------|-------------------|------------|------|
| 语言生态 | Python，Go 支持差 | 成本高 | **原生 Go**，与团队技术栈一致 |
| 编排能力 | Graph/Agent 成熟 | 需自实现 | **Graph + ReactAgent + ADK 三模式** |
| 企业级组件 | 无 | 全自研 | MCP、RAG、SSE 配套组件 |
| 状态持久化 | 无内置 | 自实现 | 节点级状态持久化，支持断点续跑 |
| 社区维护 | Python 主社区 | 无 | 字节内部开源，持续迭代 |

**落地踩坑**：

1. **会话状态覆盖**：初期节点状态存储粒度太粗，多租户并发导致会话覆盖。解决方案：Redis Key 增加租户前缀隔离，增加会话分布式锁。
2. **ReAct 无限循环**：工具调用失败后模型持续重试。解决方案：`MaxStep=25` 硬限制 + 兜底分支自动降级。
3. **SSE 流式中断**：客户端断开后模型仍在推理。解决方案：监听连接关闭信号，立即 `cancel()` 上下文终止推理，避免无效 Token 消耗。
