# 简历定制技能 (Resume Tailoring)

针对特定 JD 生成定制化简历，通过内容匹配打分、经验挖掘、子弹点重构和术语对齐，在保持事实完整性的前提下最大化匹配度。

## 核心原则

1. **事实保全**：绝不编造经历，但智能重构和强调相关内容
2. **透明打分**：每条子弹点标注匹配维度和置信度
3. **经验挖掘**：通过分支对话发现未记录的隐性经验
4. **STAR 结构**：所有子弹点遵循"背景 → 技术方案 → 评测效果"三段式

## 工作流程

### 第一步：JD 解析与需求拆解

1. 读取用户提供的 JD，提取：
   - 硬性要求（学历、语言、经验年限）
   - 技术要求（框架、工具、方法论）
   - 加分项（优先经验）
   - 团队定位关键词（如：研发效能、开发者基础设施、软件全生命周期）
2. 将 JD 需求逐条拆解为可打分维度

### 第二步：内容匹配与打分

对每段项目经历，使用 **4 维匹配模型** 打分：

| 维度 | 权重 | 说明 |
|------|------|------|
| Direct Match | 40% | 关键词、领域、技术、产出直接对齐 JD |
| Transferable | 30% | 同等能力在不同上下文中的应用 |
| Adjacent | 20% | 相关工具、方法、问题空间 |
| Impact | 10% | 成就类型与目标角色价值对齐 |

**置信度分级**：
- 90-100%: DIRECT — 直接使用
- 75-89%: TRANSFERABLE — 强候选
- 60-74%: ADJACENT — 重构后可用
- 45-59%: WEAK — 仅无更好选择时使用
- <45%: GAP — 标记为未覆盖需求

### 第三步：内容重构策略

**策略 1: Keyword Alignment（关键词对齐）**
- 保留事实，将术语对齐到 JD 用语
- 例：`智能运维` → `研发效能`
- 例：`评测` → `评估体系`

**策略 2: Emphasis Shift（强调转移）**
- 同样事实，变换聚焦点
- 例：`告警诊断` → `研发故障诊断`
- 例：`Ops 故障诊断链路` → `多步推理 Agent 链路`

**策略 3: Abstraction Level（抽象层级调整）**
- 从实现细节提升到方法论层面
- 例：`Python 脚本批量调用 HTTP 接口` → `批量评测脚本`
- 例：`路由、RAG、日志检索` → `路由分发、检索召回、工具调用、指标计算和综合诊断五大维度`

**策略 4: Scale Emphasis（规模强调）**
- 强调协作深度和影响范围
- 例：`撰写文档` → `主导核心架构设计文档输出与技术方案评审`
- 例：`跨团队协作` → `跨角色协作，推动接口规范统一`

### 第四步：STAR 子弹点方法论

所有项目职责必须遵循 **背景（Problem）→ 技术方案（Action）→ 评测效果（Result）** 结构：

```
针对 {背景问题}，通过 {技术方案}，实现/支撑 {评测效果}。
```

**改写示例**：

| 维度 | 改写前 | 改写后 |
|------|--------|--------|
| 架构设计 | 抽象 ModelRouter / RAG / ToolGateway 等核心模块 | **针对**传统运维知识分散、故障排查依赖人工经验的问题，抽象五大模块，**支撑**故障诊断从人工排查升级为 Agent 自动推理 |
| RAG 链路 | 实现 Markdown 文档上传、分块、Embedding 向量化 | **为解决**故障手册检索不准、知识无法进入诊断上下文的问题，实现 RAG 全链路，**Citation 机制确保**答案可溯源 |
| 工具治理 | 抽象工具注册表、风险分级、RBAC | **针对** Agent 直接调用外部系统存在权限失控、调用不可审计的风险，建立治理框架，**每次调用均可追溯、可审计** |
| 评估体系 | 构造评估用例，统计路由正确率 | **覆盖**五大维度，通过批量评测形成可量化评估闭环，**为** Prompt 优化、检索分块和工具描述迭代提供数据支撑 |

### 第五步：Title Reframing（角色名称重构）

在不改变事实的前提下，将角色名称调整为更精准、更体现职责的表述：

| 原则 | 说明 |
|------|------|
| 突出真实职责 | 独立主导 0-1 → `Agent 平台负责人` |
| 精确描述角色 | 沙箱核心开发 → `沙箱运行时核心研发` |
| 强调相关方面 | 安全相关开发 → `安全模块核心开发` |

**约束**：
- 绝不声称未做过的工作
- 不过度夸大职级
- 公司名和日期必须准确

### 第六步：经验挖掘（Branching Discovery）

当发现匹配缺口时，使用分支对话挖掘未记录的经验：

**技术缺口模式**：
```
初始探测："JD 要求 {技能}，你有相关经验吗？"
├── 有 → 深挖：规模？生产环境？具体挑战？指标？
├── 间接 → 角色是什么？学到了什么？
├── 相邻 → 相关技术经验？可迁移？
├── 个人学习 → 项目/课程？近期程度？
└── 完全没有 → 尝试更宽泛的类别，或标记为缺口
```

**软技能缺口模式**：
```
初始探测："JD 强调 {软技能}，讲一下你展示过这点的经历"
├── 强示例 → 深挖：参与方？挑战？结果？指标？
├── 模糊 → 重新表述问题，提供具体场景
├── 项目相关 → 角色？协调对象？如何确保对齐？
└── 志愿/副业 → 范围？时间线？可衡量的成果？
```

## 输出格式

每次分析完成后，输出以下结构化报告：

```markdown
## 一、JD 需求拆解与匹配综述

| JD 需求 | 最佳匹配来源 | 维度 | 置信度 |
|---------|-------------|------|--------|
| 需求1 | 项目X | DIRECT | 95% |
| 需求2 | 项目Y | TRANSFERABLE | 78% |

## 二、逐项目子弹点评分

| 子弹点 | 关键词对齐 | 可迁移性 | 影响力 | 综合 | 置信度 |
|--------|-----------|---------|--------|------|--------|

## 三、差距与重构建议

| 位置 | 策略 | 当前 | 建议 |
|------|------|------|------|

## 四、可执行修改清单

| 优先级 | 修改项 | 影响 |
|--------|--------|------|
```

## 使用示例

```
用户：帮我分析这份 JD 和我的简历的匹配度
JD：[粘贴 JD]
简历：[路径或内容]

Skill 执行：
1. 解析 JD → 提取 10 项需求
2. 逐项匹配简历 → 计算置信度
3. 识别 3 个 GAP、5 个需要重构的子弹点
4. 输出结构化分析报告 + 具体修改建议
```
