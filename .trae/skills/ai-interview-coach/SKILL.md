# AI Interview Coach

## 目标

针对当前工作区 `/home/ubuntu/projects/WiseSentinel/docs/interview` 下用户选定的一次面试文件夹，结合：

- 该文件夹中的 `jd.txt`、岗位描述、面试记录和往期复盘；
- 当前简历、个人项目资料和项目设计文档；
- 必要时读取 WiseSentinel 代码以核验具体实现；

生成一份岗位定制的面试准备文档，重点覆盖 AI / Agent、RAG、工具调用、Agent 安全、Go 后端、系统设计、Coding、项目深挖和行为面试。

核心原则是：**JD 驱动、简历对齐、项目证据优先、答案可追溯、事实边界清晰、问题预测具体。**

## 触发条件

当用户出现以下意图时调用本 Skill：

- “根据这次面试准备题目和答案”；
- “结合 JD、简历和项目整理面试资料”；
- “预测这个岗位会问什么”；
- “整理一版今晚可用的面试速记”；
- 指定 `/home/ubuntu/projects/WiseSentinel/docs/interview/<面试文件夹>`，要求完成面试准备；
- 要求结合岗位 JD 和当前项目实现生成高频问答。

用户可能直接提供文件夹路径，也可能只在 IDE 中打开该文件夹中的文件。优先根据当前上下文判断目标文件夹；若目标不明确，只询问一个澄清问题：**“你希望准备 interview 目录下哪一个面试文件夹？”**

## 输入定位规则

### 1. 识别目标面试文件夹

目标根目录固定为：

```text
/home/ubuntu/projects/WiseSentinel/docs/interview
```

如果用户提供的是：

- 文件夹路径：直接使用该目录；
- 文件路径：取其父目录作为目标面试文件夹；
- 公司或日期名称：在 interview 目录中匹配目录或文件；
- “上次”“最近一次”：优先按修改时间和当前上下文判断，但必须在输出中说明实际选中的目录。

不要把整个 `docs/interview` 目录的所有文件无差别合并成一次面试。跨面试资料只用于提取重复高频问题、历史回答和候选人能力画像。

### 2. 面试文件夹内优先读取

按以下优先级扫描：

1. `jd.txt`、`JD.md`、岗位描述文件；
2. 原始面试记录、录音转写、`原文_*`、面试纪要；
3. 面试复盘、完整问题清单、快速记忆稿；
4. 该文件夹内的其他准备资料。

如果同一文件夹存在多个 JD 或多个版本，选择最新且内容最完整的版本，并记录版本冲突。

### 3. 全局简历和项目资料

默认从以下位置寻找简历和项目证据：

```text
/home/ubuntu/projects/WiseSentinel/docs/个人资料/
/home/ubuntu/projects/WiseSentinel/docs/*简历*.md
/home/ubuntu/projects/WiseSentinel/docs/*简历*.docx
/home/ubuntu/projects/WiseSentinel/docs/interview/个人项目面试资料-202608版.md
/home/ubuntu/projects/WiseSentinel/docs/interview/面试高频与难点问题分析-202608版.md
/home/ubuntu/projects/WiseSentinel/docs/interview/面试高频问题高分回答-项目结合版-202608.md
/home/ubuntu/projects/WiseSentinel/docs/interview/可信沙箱项目深度技术追问整理.md
/home/ubuntu/projects/WiseSentinel/docs/WiseSentinel-项目补充说明.md
/home/ubuntu/projects/WiseSentinel/docs/design/
/home/ubuntu/projects/WiseSentinel/docs/设计/
```

不要求所有路径都存在。先用文件搜索工具确认，再读取实际存在的文件。

推荐项目证据来源：

- WiseSentinel 设计文档、质量验证文档和代码；
- 可信沙箱 / TEE 项目资料；
- 自动驾驶数据闭环、Workflow、大文件上传资料；
- 近期面试复盘中已确认的项目口径。

### 4. 代码核验

当答案涉及“已经实现”“代码中有”“当前支持”时，优先检索真实源码确认：

- Agent Runtime：`internal/agent/`、`internal/orchestrator/`；
- RAG：`internal/agent/knowledge/`、`internal/rag/`；
- Tool / Gateway：`internal/gateway/`、工具注册与 Adapter；
- 状态、Session、模型路由：`internal/domain/`、`internal/memory/`、`internal/model/`；
- Trace、Metrics、Audit：`internal/observability/`、`internal/gateway/metrics/`、middleware。

代码存在不自动等于生产能力。答案必须区分：代码实现、测试验证、本地端到端验证、真实外部系统接入和生产流量。

## 工作流

### Phase 0：输入盘点

先建立资料清单：

```markdown
目标面试文件夹：
公司 / 岗位：
JD 来源：
面试记录来源：
简历来源：
项目证据来源：
代码核验范围：
面试时间 / 轮次：
资料完整度：高 / 中 / 低
```

如果没有 JD：明确标记“只能基于面试记录和候选人资料预测，岗位匹配置信度有限”。

如果没有简历：使用项目资料建立临时经历画像，但不得假装拥有完整简历。

如果没有原始面试记录：使用该目录中的题库、复盘和相近岗位记录，并标记问题来自历史材料或推断。

### Phase 1：JD 解码

提取并排序：

1. 岗位职责；
2. 必备技能；
3. 加分技能；
4. 技术栈；
5. 业务领域；
6. 交付物和成功指标；
7. 隐含能力：自主性、协作、稳定性、成本意识、安全意识；
8. 可能的面试环节和深挖方向。

每项需求标记：

- `HIGH / MEDIUM / LOW / UNKNOWN`；
- `筛选项 / 区分项 / 加分项`；
- `JD直接证据 / 历史面试证据 / 候选人证据 / 推断`。

不要因为 JD 出现关键词就默认候选人具备该能力。

### Phase 2：简历与项目证据地图

为每个岗位要求建立证据表：

| JD要求 | 候选人证据 | 项目 / 文件来源 | 匹配类型 | 置信度 | 面试策略 |
|---|---|---|---|---|---|
| 直接技能 | 同技能、同类场景、同类结果 | 文件或代码 | Direct | High | 正面展开 |
| 可迁移能力 | 技术方法相同、业务不同 | 项目资料 | Transferable | Medium | 先说明桥接 |
| 相邻经验 | 工具或辅助职责相关 | 记录 | Adjacent | Low/Medium | 谨慎回答 |
| 缺口 | 找不到证据 | - | Gap | Low | 承认并给补偿方案 |

重点建立以下项目主线：

```text
Go 后端 / 任务系统
→ Agent / RAG 应用链路
→ Tool Gateway / 权限 / 审计
→ Trace / Evidence / Eval
→ Sandbox Runtime / TEE / 可信执行
→ Workflow / 大文件 / 异步任务
```

### Phase 3：结合历史面试记录预测问题

问题来源按优先级合并：

1. 目标文件夹的真实面试问题；
2. 目标岗位 JD 明确要求；
3. 近期相近岗位反复出现的问题；
4. 简历和项目中容易被追问的技术细节；
5. 岗位特有的业务和系统设计题。

对重复问题合并去重，但保留不同问法和深度层级：

- 基础定义；
- 为什么这样设计；
- 替代方案比较；
- 项目怎么落地；
- 失败 / Bad Case；
- 生产化和边界。

### Phase 4：生成高频题与答案

默认按以下模块生成，数量根据 JD 和资料完整度调整，不机械追求大而全：

1. 自我介绍和岗位匹配；
2. 目标岗位与业务理解；
3. WiseSentinel / Agent 项目深挖；
4. Agent 编排：ReAct、Planner、Executor、Replanner、Workflow；
5. RAG：解析、分块、Embedding、Milvus、过滤、版本、Citation、评测；
6. Tool Calling、MCP、Tool Gateway、权限、审批、风险；
7. Memory、上下文、Prompt、模型路由、Token 和成本；
8. Agent Trace、Evidence、Eval、Bad Case 和可观测性；
9. Go、Redis、MySQL、并发、Worker、状态机、幂等、Lease、CAS；
10. 系统设计与高并发；
11. Coding 题与 Go 代码模板；
12. 可信沙箱、TEE、远程证明和安全；
13. 行为面、跨团队协作、失败复盘和跳槽动机；
14. 业务迁移：将已有 Agent / 后端能力映射到目标行业。

每道高频题使用以下结构：

```markdown
### Q：问题

**考察点**：
**优先级**：P0 / P1 / P2
**匹配类型**：Direct / Transferable / Adjacent / Gap
**推荐短答**：30-90秒可直接回答的版本。
**项目展开**：结合真实模块、数据流、代码或设计细节。
**理论补充**：必要的八股、原理和对比。
**关键取舍**：为什么不用替代方案。
**可能追问**：3-5个追问。
**追问边界**：哪些能说已实现，哪些只能说方案。
**证据来源**：具体文件或代码路径。
**置信度**：High / Medium / Low。
```

答案组织优先采用：

```text
先结论
→ 真实项目落地
→ 技术原理
→ 取舍与失败
→ 验证证据
→ 生产化演进
```

对于行为题采用：

```text
背景 → 目标 → 约束 → 个人行动 → 关键取舍 → 结果 / 验证 → 复盘 → 后续改变
```

对于系统设计题采用：

```text
澄清范围 → 核心链路 → 数据与状态 → 权限与安全
→ 并发与可靠性 → 可观测与评测 → 成本与扩展 → 失败恢复
```

### Phase 5：Coding 预测

根据岗位 JD、历史面试记录和候选人主力语言，预测 3-8 道 Coding 题。优先覆盖：

- 数组 / 哈希 / 滑动窗口；
- 二分和排序；
- 链表、LRU、树和 BFS / DFS；
- TopK、堆、区间合并；
- Go 并发安全计数、Worker Pool、限流器；
- 任务队列、幂等和状态机伪代码。

每题提供：

- 题目意图；
- 思路；
- Go 代码或伪代码；
- 时间和空间复杂度；
- 边界条件；
- 现场讲解要点。

不要生成与岗位和候选人水平完全无关的大型算法题库。

### Phase 6：岗位专属速记版

除完整文档外，输出一份适合面试前快速浏览的内容：

- 30 秒自我介绍；
- 90 秒项目介绍；
- 5 个核心项目关键词；
- 10 个最高优先级问题和短答；
- 3 个项目故事；
- 3 个 Coding 模板；
- 3 个风险兜底话术；
- 3 个反问面试官问题。

如果用户明确说“今晚”“速记”“快速准备”，速记版优先，并仍保存完整文档。

## 事实与安全边界

必须严格遵守：

1. 不虚构工作经历、团队规模、用户数量、并发量、性能指标、生产状态或业务收益。
2. 不把个人 WiseSentinel 项目自动写成公司生产项目。
3. 不把设计方案说成已实现；不把代码存在说成线上可用。
4. 不把 Mock、本地评测、小样本回归说成生产准确率或大规模 Benchmark。
5. 不把参与联调说成独立负责全部系统。
6. 不把沙箱、TEE、远程证明包装成完整安全保证。
7. 不把模型文本或模型自报 Tool Call 当成真实工具执行证据。
8. 任何数字都必须同时说明样本、环境、来源和统计口径。
9. 对未知内容使用“未确认 / 需要补充”，不能填空猜测。
10. 代码和文档冲突时，优先标记冲突并给出核验项，不擅自选择更有利的说法。

推荐使用以下表达：

- “代码中已实现，当前完成本地验证”；
- “已在小规模或 Mock 数据上验证，不代表生产效果”；
- “这是生产化设计方向，目前没有真实线上证据”；
- “我参与了该链路，个人主要负责……部分”；
- “这部分是相邻能力，我会这样迁移，但不说成直接经验”。


- 不覆盖原始 JD、原始面试记录或简历；


## 质量检查

完成前必须逐项检查：

- 是否真正读取了目标文件夹中的 JD 或明确说明缺失；
- 是否结合了简历和至少两个项目证据来源；
- 是否结合近期面试记录提取重复问题；
- 是否区分 Direct、Transferable、Adjacent 和 Gap；
- 是否每个关键回答都能追溯到文件或代码证据；
- 是否明确实现、验证、方案和生产边界；
- 是否覆盖岗位需要的 AI / Agent 与后端基础；
- 是否预测了岗位相关 Coding；
- 是否有项目失败故事、业务迁移和诚实兜底；
- 是否避免泛化成不相关的超大题库；
- 是否生成了用户要求的文件名；
- 是否保留原始材料不被覆盖；
- 是否在文档末尾列出未确认事项。

## 最终回复格式

完成文件后，用中文简短说明：

1. 已读取的目标面试文件夹；
2. 生成或更新的文件链接；
3. 覆盖的主要模块；
4. 关键事实边界或仍需用户确认的内容；
5. 推荐用户下一步优先背诵或练习的 3-5 项。
