# 阶段 83：模型准入容量可观测性

日期：2026-08-11

## 问题与根因

共享模型预算已能返回 `50304`，但仅从请求结果无法判断当前预算是否长期饱和、释放是否泄漏，或拒绝量是否在增长。没有在途/拒绝指标，容量治理只能依赖日志和偶发压测。

## 落地

新增低基数 Prometheus 指标：

- `ws_model_admission_in_flight{provider}`：当前持有本地模型准入槽位的调用数；
- `ws_model_admission_rejections_total{provider}`：因本地预算已满而拒绝的次数。

provider 使用已有受控分类；模型名、部署 URL、tenant、提示词、API key 和错误正文均不进入 label。Generate 与 Stream 在获取槽位时递增，在所有释放路径递减；预算满时仅增加 rejection counter。

## 验收证据

- observability/model 单测确认未知 provider 被压缩为 `other`、拒绝计数增长、release 后 gauge 回到 0；
- 真实 4 并发 SSE：3 个 `success_done`、1 个 `sse_50304_retry_2`；
- 压测结束后 `/metrics` 显示：

```text
ws_model_admission_in_flight{provider="openai"} 0
ws_model_admission_rejections_total{provider="openai"} 1
```

说明过载可被观测，且本轮没有准入令牌泄漏。

## 生产建议

按 provider 计算 rejection rate、in-flight saturation duration 和模型调用 P95；设置“持续饱和/拒绝率超阈值”告警。多副本部署还需要汇总实例指标并结合全局供应商预算，单实例 gauge 不可当作集群总量。
