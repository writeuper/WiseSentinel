# 阶段 2：审批状态完整性

- 日期：2026-08-10
- 状态：已完成 P0 状态完整性修复；“批准后受控执行”待独立设计决策
- 协作角色：Agent 架构师、自动化测试工程师、Golang 后端工程师

## 1. 问题与影响

WiseSentinel 原有审批链路只实现“建单 → 改为 approved/rejected”。批准后并不会恢复工具调用；过期审批既可能继续出现在待办列表，也可能被批准；审批路由也未进入 HTTP 审计。由此无法建立可信的高风险动作治理闭环。

## 2. 根因

- `ListPending` 和 `Decide` 只判断 `status=pending`，没有把 `expired_at` 纳入读取和 CAS 条件。
- `ExpireStale` 没有在列表/决策路径调用。
- 审批路由不在审计 action 映射中。
- 审批记录缺少执行 token、执行结果、outbox、工具快照及工作流 continuation；因此“approved”并不等同于“已经受控执行”。

## 3. 企业级方案与范围取舍

企业级 L2 操作应采用两段式状态机：

```text
pending → approved → execution_queued → executing → executed | execution_failed
pending → rejected | expired
```

批准与执行必须分离。执行端应从不可变审批快照恢复操作，重新检查租户、策略、工具版本和授权，并使用 outbox + fencing token 保证一次或幂等执行。对于当前 Ops Plan-Execute-Replan 链路，不能在没有持久化 checkpoint 的情况下“重跑整个 Agent”来恢复某一步审批，否则会带来重复工具调用和不确定性。

本阶段先完成不依赖业务策略选择的 P0 修复：过期决策防护、列表过滤、决定 CAS 和审计。完整恢复需要以下待确认或新增能力：真实 L2 工具/受控 adapter、审批人职责分离（是否允许申请人自批、是否双人/MFA）、outbox/执行 Worker，以及 Agent 的 durable step checkpoint。

## 4. 落地实现

- `ApprovalRepo.GetPending`、`ListPending`、`Decide` 均加入 `expired_at > now` 条件。
- Controller 在列表和决策前调用 `ExpireStale`，使过期单落为 `expired`。
- 审批路由纳入 `approval.decide` 审计 action。
- 新增 MySQL integration test：验证过期单不能批准、不会出现在待办列表；两个并发决策恰好一个成功。
- 新增 `make test-approval-integration` 门禁。

## 6. 遗留风险与下一阶段

当前 `approved` 仍只表示审批决定已提交，**不代表工具已执行**。下一阶段必须在确定审批策略后实施批准恢复 Worker；在此之前，不应新增实际 L2 写工具或将现有审批 UI 宣传为“自动恢复执行”。
