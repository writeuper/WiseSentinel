# 阶段 57：Repository 空结果与资源不存在契约统一

日期：2026-08-11

## 根因

不同 repository 对 GoFrame `Scan`/`GetScan` 的 `sql.ErrNoRows` 处理不一致。Session 与 Trace 已分别暴露为 500；系统审计发现 OpsTask、Document、FaultKnowledge、DocumentIndexState、VectorGC 和 AlertEvent 读取同样可能将正常的“不存在”变成内部错误。

这会泄露数据库实现细节、破坏前端错误恢复和 API 幂等语义，并使监控中的 5xx 误报放大。

## 实现

所有上述 `Get`/去重读取在 repository 边界统一将 `sql.ErrNoRows` 映射为 `(nil, nil)`；handler 继续以领域资源不存在返回 `40401`。数据库异常仍原样向上返回，未将真正的连接、权限或一致性错误吞掉。

## 企业级原则

- “资源不存在”是预期业务状态，不是基础设施故障。
- 仓储层归一化 driver 差异，服务/handler 层决定 404、幂等成功或创建竞争恢复。
- 多租户资源读取仍以 tenant 条件约束；404 不区分不存在与无读取权限，避免枚举。

## 回归证据

| 验收 | 结果 |
| --- | --- |
| Repository / Handler 单元回归 | 通过 |
| MySQL Trace canary 集成（含 missing trace） | 通过 |
| 真实 GET missing Ops task | HTTP 404，`code=40401` |
| 真实 DELETE missing document | HTTP 404，`code=40401` |
| 敏感 sink 静态门禁 | 通过 |
| 新构建服务健康检查 | 通过 |

## 后续

新增 repository 单记录读取时应复用本语义并加入 missing-resource 契约测试；可进一步封装一个受测的 `IsNoRows` helper，避免未来遗漏。
