# 阶段 38：Compose 迁移门禁

## 问题根因

Docker Compose 仅将 `schema.sql` 挂载给 MySQL 首次初始化。已存在的数据卷不会再次运行 init scripts，因此新增加的 `lease_expires_at`、GC outbox 等 migration 在升级环境中不会自动生效；集成测试和应用会出现“本地已经手工迁移、干净部署缺列”的漂移。

此外，早期 Index/Ops lease migration 使用裸 `ALTER TABLE`，无法安全重放，不能作为可靠的启动 job 输入。

## 企业级方案与落地

- 将早期 Index/Ops lease migration 改为 `information_schema + PREPARE` 的幂等 DDL，fresh schema 与已升级数据库均可重复执行。
- Compose 新增一次性 `migrate` job：仅在 MySQL healthcheck 成功后，按文件名顺序执行 `/migrations/*.sql`。
- `platform` 依赖 `migrate: service_completed_successfully`，拒绝在 schema 未完成迁移时启动。
- 新增 `make migrate`，用于在现有 Compose 数据卷上显式重放 idempotent migrations。

## 缺陷闭环

首个 Compose 实现将 shell `command` 写为折叠字符串；Compose 将其拆为多个参数，`/bin/sh -ec` 仅得到 `for` 并报语法错误。第二次改为把完整循环作为 entrypoint 的第三个参数；Compose interpolation 使用 `$$file` 保留容器内 shell 变量。

## 验证

```bash
docker compose -f manifest/docker/docker-compose.yml config
make migrate
make migrate # 再次执行，验证幂等
```

结果：migration job 按顺序执行 document generation、Index/Ops lease、GC outbox 与 Index DB lease，重复运行无 DDL 冲突。

## 风险与后续

- migration job 使用 Compose 内开发账号，生产环境须由受管 secret 与受限 migration service account 替换，不能复用开发密码。
- 当前数据库没有 `schema_migrations` 版本审计表；脚本自身幂等保证安全重放，但后续应引入版本记录、checksum 和部署审计事件。
