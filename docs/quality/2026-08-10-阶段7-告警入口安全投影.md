# 阶段 7：告警入口安全投影

## 根因

Alertmanager Webhook 的签名原始 body 被直接写入 `ws_alert_event.payload_json`，而 alert annotations 又被拼接到 Ops query。告警 annotation、`generatorURL` 和外部系统标签可能携带 Bearer Token、签名 URL、邮箱或日志片段，从而把外部输入扩散到数据库与模型上下文。

## 企业级方案

Webhook 原始 body 仅应服务于验签、事件指纹和短时处理；长期观测记录保存脱敏投影。外部告警文本在进入 LLM/Agent 前同样按最小披露原则清洗。若未来需要保留原始告警用于合规取证，应放入独立的 KMS 加密、短 TTL、审计访问证据仓，而不是业务事件表。

## 落地

- `handleAlertmanager` 仍以原始 body 计算 SHA-256 event ID，保持去重语义。
- 所有 alert description 在构造 Ops query 前调用 `redact.Summary`。
- `ws_alert_event.payload_json` 在 handler 与 repository 两层调用 `redact.JSON`，形成防御纵深。

## 回归证据

本阶段复用阶段 5 的 JSON/文本 canary 覆盖，验证敏感字段、Bearer、DSN、URL 参数和邮箱均不会出现在安全投影中。已执行：

```text
go test ./internal/pkg/redact ./internal/gateway/handler ./internal/repository
make verify
```

均通过。

## 遗留项

- 现有告警事件历史数据仍需单独清理和密钥轮换。
- Alertmanager 允许的 labels/annotations 尚未使用字段 allowlist；下一轮应保留告警名、严重级别、服务名等显式业务字段，并为长文本设置上限。
- 生产 Webhook 的速率限制、来源网络隔离和告警 payload 的真实端到端 canary 测试仍需在隔离环境验证。
