# 阶段 64：隔离并发 Chat 回归与会话清理

日期：2026-08-11

## 问题与根因

真实并发评测需要为每个虚拟用户创建独立会话。原平台只有创建、读取和列表 API，没有受对象授权保护的会话删除能力；自动化测试会留下 MySQL 会话记录和 Redis 短期记忆，污染后续评测与运行指标。共享租户的会话总数也无法证明某次测试资源已被精确清理。

## 企业级方案

测试资源必须使用独立命名空间、可识别前缀和精确 cleanup，并在 cleanup 后以资源级读取验证，而不是依赖共享总数。会话删除采用：服务端对象级授权 → MySQL 状态围栏 → Redis 历史删除。关系库与 Redis 没有分布式事务，因此先持久化停用权限围栏；Redis 短暂故障最多留下不可再通过正常 API 读取的 TTL 数据，不会使已删除会话重新可访问。

## 实现

- 新增 `DELETE /api/v1/sessions/{session_id}`；复用 Chat/历史读取的对象级授权，不信任客户端身份。
- `ws_session.status=0` 是持久访问围栏，`SessionRepo.Get` 仅返回 active 会话；重复删除不产生新的副作用。
- 删除后清除该会话的精确 Redis history key。
- 新增 `scripts/run_concurrent_chat_load.py` 与 `make agent-load-chat`：创建独立会话、关闭 RAG/工具以隔离模型并发、只输出聚合结果、删除后再用历史接口 404 验证 cleanup。
- 统计只含 requests/successes/失败类别/cleanup 类别/P50-P99，不保存 API key、回答、问题、Trace 内容或原始 HTTP body。

## 容量结论与后续

本轮仅是低风险 2 并发真模型 canary，证明会话隔离、清理与基础并发路径可用，不代表生产峰值承载。预发布应按模型配额分级增加并发（2→5→10），设置请求总预算和中止阈值，并分别报告成功率、429、超时、P50/P95/P99、模型阶段耗时、Redis/MySQL 连接池饱和度和 goroutine。高风险工具与 L2 写执行不在该压测范围内，仍保持 fail-closed。
