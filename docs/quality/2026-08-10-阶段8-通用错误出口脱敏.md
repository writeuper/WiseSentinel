# 阶段 8：通用错误出口脱敏

## 根因

阶段 5 保护了工具网关、Trace 和主要 API 投影，但通用 `UnifiedResponse` 会把非 `AppError` 的 `err.Error()` 原样返回。模型、RAG、网络或第三方适配器的错误正文可能携带 Token、连接串和请求上下文。Recovery panic 日志与 RAG 索引错误日志/任务错误也存在同类旁路。

## 企业级方案

错误在边界处应分为稳定业务类别和安全诊断摘要：HTTP 客户端获取脱敏摘要，日志/任务记录也只保留脱敏摘要；关联通过 trace ID、状态码和错误类别完成。底层错误原文如确有取证需求，必须进入独立受控证据仓。

## 落地

- `UnifiedResponse` 对未知错误使用 `redact.Summary` 后再输出。
- Recovery 对 panic 文本先脱敏再记录日志，客户端保持稳定内部错误。
- RAG 索引的 source URI 和错误写日志/任务表前均转换为安全投影；`IndexTaskRepo` 对两类完成方法做防御性脱敏。
- `redact` 新增 `dsn`/`connection_string` 敏感字段，补充 Go MySQL DSN (`user:password@tcp(host)/db`) 文本规则及 canary。

## 回归证据

```text
go test ./internal/pkg/redact ./internal/gateway/middleware ./internal/rag ./internal/repository
make verify
```

均通过。

## 遗留项

- 对 `AppError` 的自定义消息仍依赖调用点不得拼接原始上游 body；后续应增加静态 sink 规则和错误分类 API，禁止 `fmt.Errorf` 原文贯穿边界。
- 模型、Prometheus、MCP、DashScope 等 adapter 仍应逐步改为只保留 provider/status/request-id 的稳定错误，而不是先读取完整错误 body 后依赖出口脱敏。
- 需要在真实 HTTP 服务中注入带 canary 的上游 4xx/5xx/panic，采集响应、stdout 和数据库，形成端到端零泄露门禁。
