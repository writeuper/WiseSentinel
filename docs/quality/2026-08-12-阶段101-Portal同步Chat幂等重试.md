# 阶段 101：Portal 同步 Chat 幂等重试

日期：2026-08-12

## 用户风险与根因

真实 OnCall 用户在同步 Chat 等待模型、RAG 或工具结果时，浏览器、反向代理可能丢失响应；用户点击“重试”会再次提交同一个问题。后端从阶段 92 起已支持同步 `POST /chat` 的 durable `Idempotency-Key` 回放，但 Portal 从未传递该 header，因而无法使用已有的防重放执行边界，可能形成第二次模型/工具调用与重复会话消息。

## 角色协作结论

| 角色 | 结论与落地 |
| --- | --- |
| Agent 架构师 | 幂等键属于单一“逻辑用户回合”，不是 session、用户标识或持久浏览器状态；仅同步 API 有安全响应回放，所以 SSE 不能复用该承诺。 |
| 自动化测试工程师 | 覆盖顺序回放、同 key 并发争用、key/hash 冲突、测试 session 精确清理以及前后端 readiness；不以共享全局模型计数充当并发环境的唯一判据。 |
| Golang 后端工程师 | 复核现有 `(tenant,user,session,key)` 数据库唯一约束和 execution-token CAS：已完成回合返回相同安全投影与 Trace；运行中/失败/内容冲突均 fail-closed。此次无后端协议或迁移改动。 |
| 前端工程师 | Portal 对每次同步主动发送生成 `crypto.randomUUID()`，通过 `Idempotency-Key` header 发送；网络类失败保留该 key，点击“重试发送”复用；编辑输入、新发送或显式 API 拒绝会改用新 key。key 不落 localStorage、不进 URL、不展示。 |

## 实现与状态语义

- `portal/src/api/client.ts`：`sendChat` 接收可选 key，并仅以 HTTP header 传递。
- `portal/src/pages/Chat.tsx`：将重试状态从纯文本升级为 `{ text, idempotencyKey }`；同一重试不会添加第二个用户消息气泡。
- 对浏览器网络失败保留 key：服务端可能已经完成，重试将安全回放，而非再调模型。
- 对已收到的 `ApiError` 不复用 key：服务端已明确该回合未完成、正在执行或被 fail-closed；新请求需是显式新执行，避免用户永久停在 `409` 冲突循环。
- 流式接口继续不传 key。它缺少经持久化的 citation/message/done 事件序列回放；为 SSE 加 header 而不实现事件回放会制造“不会重复执行”的错误预期。

## 剩余风险与下一步

1. 同步回放响应没有 `replayed` 字段，Portal 不应也不会把回放显示为“新执行”；若产品需要展示，应与 SSE event journal 统一设计后扩展 API。
2. 运行中/失败 turn 仍是 fail-closed，用户需明确新发送；尚无 lease reclaim，不能声称崩溃后的旧 key 可自动恢复。
3. 当前验证是隔离开发/集成环境的真实模型调用与两请求争用，不代表生产用户流量、区域故障、跨实例配额或峰值吞吐。生产前需将该合同接入发布环境，并按租户、公平配额和模型 profile 做容量阶梯测试。
