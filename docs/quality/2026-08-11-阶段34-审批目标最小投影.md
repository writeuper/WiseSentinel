# 阶段 34：审批目标最小投影

## 问题与根因

Vector GC 重驱已要求双人审批，但审批列表只有 `task_id`（稳定哈希引用）。批准人无法在不访问数据库的前提下验证待重驱的 document 与 target key，这削弱了职责分离的实际效果。

直接向前端返回 `ws_approval.payload_json` 不是可接受方案：payload 包含申请人、操作原因，其他审批类型还可能包含工具参数或敏感上下文。

## 企业级方案与实现

采用服务端类型化投影，而非通用 payload 回传：

- `ApprovalItem` 新增可选 `target`；仅当 `approval_type=vector_gc_redrive` 且 JSON 含完整 `doc_id + target_key` 时返回。
- 服务端只返回 `kind/doc_id/target_key`，并再次以 `redact.Summary` 限长；不返回 requester、reason、完整 payload、token 或任何工具输入。
- JSON 格式错误、不完整 payload、非 Vector GC 审批都 fail-closed 为无 target。
- Portal 审批列表和确认 Modal 仅对该类型展示精确受控目标，并提醒批准人核对目标且不得自行批准；真正的职责分离仍由后端事务验证。

## 验收与回归

| 风险 | 覆盖 | 结果 |
| --- | --- | --- |
| payload 过度暴露 | 单元测试仅断言投影字段，payload 含 `requested_by/reason/token=secret` | 通过 |
| 格式异常 | 非 Vector 类型、缺 target key | fail-closed，通过 |
| 前端契约漂移 | TypeScript 类型、审批表格/Modal、Vite production build | 通过 |
| 既有后端回归 | handler/repository 测试 | 通过 |

执行：

```bash
go test ./api/v1 ./internal/gateway/handler ./internal/repository
cd portal && ./node_modules/.bin/tsc -b --pretty false && ./node_modules/.bin/vite build
```

## 剩余风险

目前审批页面不展示申请人的受控身份投影，因此批准人只能由流程和后端拒绝得知不能自批。后续若业务需要可增加 `requester_display` 的最小化、租户内可审计投影，但必须先完成隐私与 RBAC 评审。
