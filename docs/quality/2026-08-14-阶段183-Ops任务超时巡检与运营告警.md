# 阶段183：Ops 任务超时巡检与运营告警

## 面试缺口

Ops Worker 已有 Redis 锁、数据库 CAS 和 `timeout_at`，但仅有日志无法回答“有多少运行中任务被回收、回收器是否持续成功、数据库故障期间是否可能积压”。没有独立指标时，任务完成率和失败率也难以区分 Agent 失败、依赖故障和超时回收。

## 落地内容

- `OpsWorker.tick` 每轮调用 `ExpireTimedOut`，现在记录：
  - `ws_ops_task_timeouts_total`：被围栏为 timeout 的任务数量；
  - `ws_ops_task_reaper_runs_total{outcome=success|error}`：超时巡检周期结果。
- 指标标签固定为受控枚举，不写入租户、任务 ID、错误正文或数据库连接信息。
- 失败周期仍保留原有日志并继续执行安全的 pending 扫描；不会把巡检失败伪装成“没有超时任务”。
- 新增 Prometheus 告警：任务超时告警和巡检错误告警。

## 可靠性语义

1. `ExpireTimedOut` 只更新 `status=running` 且 `timeout_at <= now` 的任务，并清空执行 token；迟到 Worker 仍无法通过 `FinishIfOwned` 覆盖 timeout 终态。
2. 计数器只接受正数；负数不会抵消历史超时统计。
3. reaper `error` 与 `success` 分开计数，不能把数据库错误解释为零超时。
4. 指标是任务状态机证据，不等于业务恢复成功；恢复效果仍需结合 Agent 任务完成率、工具失败率和人工升级记录。

## 测试与限制

- 单元测试覆盖超时计数单调性、受控 outcome 标签和未知值归一化。
- 既有 Ops Lease/CAS 集成测试继续验证租约抢占、迟到完成和 bounded retry。
- 当前指标是应用实例 Prometheus 指标；多副本部署必须在 PromQL 中聚合，不能把单实例值当作全局任务数。
- 数据库持续不可用时，巡检错误会告警，但不会在没有数据库证据的情况下强行修改 running 任务；需要依赖恢复后由下一轮安全回收。
