# 阶段 56：指标高基数与 Trace 负向契约治理

日期：2026-08-11

## 发现与根因

Prometheus 实例中观测到 `ws_http_request_duration_seconds`/`ws_http_requests_total` 使用实际 `/api/v1/traces/<trace_id>` 作为 `path` label。每次 Trace 查询都会生成新时序，造成高基数、Prometheus 存储/查询放大，并把关联标识传播到指标平面。

真实负向请求还发现不存在 trace 的 repository `Scan` 将 `sql.ErrNoRows` 向上传递，HTTP 接口返回 500，而非资源不存在的 404。

## 企业级方案与实现

- 指标只使用路由模板，不使用资源 ID、trace ID、文档 ID 或 Vector GC target key。
- 补齐 Trace、故障知识和 Vector GC 多段路径的 metric path 归一化；Vector GC 同时收敛 doc ID 与 target key。
- `AgentTraceRepo.Get` 将 `sql.ErrNoRows` 标准化为 `(nil, nil)`，handler 返回稳定 `40401`，不泄露数据库错误。

这遵循观测边界：trace ID 应位于受控 Trace 查询/审计链路，而不是作为 metrics label；metrics 保留 method、route template、status 和延迟即可满足 SLO、告警与容量分析。

## 后续

- 对每个新 API 路由在发布门禁中校验无动态 label；推荐由 router template 自动提供指标 path，减少手工映射遗漏。
- 阶段 55 的 P95 需要进一步按 route、agent type、RAG、provider 拆分；此次修复保证 Trace 查询本身不会污染全局 HTTP 延迟与时序基数。
