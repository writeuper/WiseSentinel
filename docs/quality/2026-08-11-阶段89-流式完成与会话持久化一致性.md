# 阶段 89：流式完成与会话持久化一致性

日期：2026-08-11

## 问题与影响

此前 Chat SSE 会在 Redis 会话窗口写入前直接转发上游 `done`，且忽略 `AppendMessages` 的失败。用户界面可能已经呈现“完成”，但刷新后无法读取该轮上下文；这会使会话连续性、任务完成率与用户可见结果发生偏差。

另一个边界是异常 EOF：浏览器端没有收到 `done` 或 `error` 时会把流自然结束当作成功，从而可能一直停留在发送态。

## 落地

- 后端在 HTTP 边界消费 SSE 时暂存 `done`，先完成用户/助手消息持久化，再发送 `done`。
- 流内出现 `error`、上下文取消或没有 `done` 标记时，均不写入会话历史。
- 会话写入失败时发送固定、无内部诊断的 SSE `error`，不再宣称完成。
- Portal 跟踪终端 SSE 事件；未收到 `done` 且也未收到 `error` 的 EOF 会显示“流式响应意外结束，请稍后重试”，避免无限发送态。

这不是端到端恰好一次语义：客户端在模型完成后、收到保存结果前断连仍需后续引入请求幂等键与会话写入状态机治理。

## 运行观察

重启时可选 MCP 时间服务初始化超时后降级，约 12 秒后服务正常启动。该行为不会阻断 readiness，但会拉长冷启动；生产部署应把 MCP 依赖的启动预算、降级计数与冷启动 SLO 纳入告警。

## 剩余风险

- Redis/DB 跨实例删除与正在生成的会话写入尚无分布式 fencing；当前删除后的 DB 访问围栏会阻止读取，但仍应在多副本生产部署前完成 session generation/version 设计。
- 当前真实证据仍只代表开发/集成环境，不代表生产用户、生产模型配额或 SLA。
