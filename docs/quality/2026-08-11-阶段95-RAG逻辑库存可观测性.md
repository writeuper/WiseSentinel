# 阶段 95：RAG 逻辑库存可观测性

日期：2026-08-11

## 问题

质量记分卡此前只能引用历史任务累计，无法回答当前 active RAG 文档和可检索 chunk 规模。将成功 index task 总数或 Milvus 历史 rows 直接当作当前 RAG 库存，会把 deleted、superseded 和待 GC 数据误计为可检索知识。

## 实现

Prometheus scrape 前以 1 秒受控数据库预算刷新以下全局、无标签 gauges：

| 指标 | 严格口径 |
| --- | --- |
| `ws_rag_active_documents` | 所有租户中 status=active 的文档数 |
| `ws_rag_active_published_chunks` | active 文档的 current `active_generation` 对应且 status=success 的 `chunk_count` 总和 |
| `ws_rag_active_legacy_documents` | active 但无已发布 generation 的 legacy 文档数 |

刷新失败仅增加 `ws_rag_inventory_refresh_errors_total`；不会把旧数值伪装为新采集结果。指标没有 tenant、doc、query、source、embedding model 或错误正文标签。

数据库逻辑明确排除 soft-deleted documents、superseded generation 和历史成功 task。该路径采用最小接口注入到 metrics handler，避免 repository → metrics → bootstrap 的依赖环。

## 测试与真实证据

- MySQL 增量集成测试：受控样本只使 active docs +2、current chunks +7、legacy docs +1；deleted document 与 99 chunks 的 superseded generation 均不计入。
- Prometheus 单测：三个库存 gauges 均为无标签 aggregate。
- 重启后实际 `/metrics` 已出现三个指标（本地集成环境快照）：13 active documents、10 active published chunks、11 active legacy documents。

该快照仅代表当前开发/集成数据库，**不代表生产规模或真实业务用户数据**。

## 未覆盖的物理向量规模

Milvus physical rows 仍不能由本指标推导：legacy vectors、superseded generation、GC backlog 和 collection compaction 都会造成差异。生产需要另建受控 collection statistics / tenant visibility 盘点，并同时展示 physical vectors、GC backlog、active logical chunks、Recall@K/MRR/nDCG 与 citation 到达率；不得把任一单项替代其他项。
