# 阶段 65：并发容量门禁与模型长尾基线

日期：2026-08-11

## 触发与根因

阶段 64 的 2 并发样本不足以说明模型并发行为。提升到 5 并发后，业务与 cleanup 均成功，但 P95 在不同轮次出现 23.806s 和 50.795s 的明显波动。仅打印摘要无法把成功率、资源清理和时延约束变成可执行发布门禁，也无法将本轮模型耗时从进程累计指标中分离出来。

## 企业级方案

容量 canary 应采用逐级并发、固定请求预算、隔离测试租户、精确 cleanup 和显式阈值。阈值必须按环境/供应商基线配置，不能在代码中硬编码为生产 SLA；门禁至少包括成功率、cleanup 完整性和 P95，上游模型耗时使用受控 metrics 差值辅助归因。

## 实现

- `run_concurrent_chat_load.py` 新增 `/metrics` 前后快照，仅汇总模型 counter 与 duration 的数值差，不写入 Prometheus labels 或任何正文。
- 新增 `--min-success-rate`、`--max-p95-ms`；`0` 表示显式关闭时延门禁。成功率不足、任一会话 cleanup 未经 404 验证、或 P95 超阈值均以非零退出，适合预发布 CI。
- `make agent-load-chat` 暴露 `LOAD_MIN_SUCCESS_RATE` 和 `LOAD_MAX_P95_MS`。
- 统计单元测试覆盖标签丢弃、metrics 差值和 cleanup/P95 门禁。

## 真实回归

```bash
EVAL_BASE_URL=http://127.0.0.1:8090/api/v1 EVAL_API_KEY=... \
  LOAD_REQUESTS=5 LOAD_CONCURRENCY=5 LOAD_MIN_SUCCESS_RATE=1 \
  LOAD_MAX_P95_MS=60000 make agent-load-chat
```

结果：5/5 成功、cleanup 5/5 verified、P50 11.681s、P95/P99 34.321s、最大 34.321s；质量门禁通过。模型 metrics 增量为 5 次成功调用、74.423s。无 429 或超时。

60s 是当前开发/集成 canary 的保护上限，不是生产 SLO。此前 5 并发轮次 P95 达 50.795s，说明模型供应商或生成长度造成长尾波动；任何生产门槛需使用冻结模型/提示词版本、足够样本、置信区间和业务方确认的用户体验目标制定。

## 后续

按 2→5→10 的阶梯继续，不超过供应商已授权配额；每一级中止条件应包含 429、超时、错误率、P95、连接池和 goroutine 上升。若 10 并发出现可复现长尾/失败，再评估调用并发隔离、排队预算、per-provider semaphore、流式 TTFT 和降级模型策略；不得仅扩大 HTTP 超时掩盖问题。
