# 阶段 39：迁移版本账本与摘要围栏

## 目标与风险

阶段 38 已使 Compose migration job 可重复执行，但“幂等”不能替代部署审计：系统不知道某个版本是否已成功应用，也无法发现历史 SQL 在已部署后被改写。这样会造成环境漂移、不可追溯的 schema 变化，且平台可能在不一致的数据库上启动。

本阶段将迁移执行从“遍历并执行”提升为受持久化版本账本约束的部署门禁。账本只保存迁移文件名、SHA-256 摘要与应用时间，不保存 SQL 正文、连接串或其他敏感内容。

## 根因与企业级方案取舍

可选方案：

1. 仅依靠 `ALTER ... IF NOT EXISTS`：可以重放，但不能审计版本或发现历史变更，未采用。
2. 引入 Flyway/Liquibase：具备成熟能力，但当前 Compose 开发部署链路较轻，额外运行时和配置迁移成本不成比例。
3. 在现有 migration job 中引入数据库账本和 SHA-256 校验：可保持已有 SQL 文件与 Compose 使用方式，同时提供版本审计、篡改检测和启动门禁，当前采用。

不变量如下：

- 每一个 `manifest/sql/migrations/*.sql` 文件至多对应一条 `ws_schema_migration` 记录。
- 已登记的迁移只能以相同摘要跳过；同名不同摘要必须失败，`platform` 不得启动。
- SQL 文件成功执行后才登记账本；若在两者之间中断，下一次可由已有的幂等 DDL 安全补偿执行。
- 账本是 MySQL 持久化状态；Redis 不参与此正确性边界。

## 落地实现

- `manifest/docker/docker-compose.yml`
  - migration job 先创建 `ws_schema_migration(migration_name, checksum, applied_at)`；文件名为主键。
  - 对每个迁移计算 SHA-256，已存在且相同则输出已校验跳过；不相同则以非零状态退出。
  - 仅在 SQL 执行成功后插入账本，`platform` 保持依赖 `migrate: service_completed_successfully`。
- `scripts/test_migration_ledger.sh`
  - 使用隔离的临时迁移目录运行篡改回归，不修改仓库 SQL。
  - 覆盖首次/重复执行、账本条目数和同名摘要不一致的拒绝路径；临时目录仅在退出时清理。
- `Makefile`
  - 新增 `make test-migration-ledger`，使本地与 CI 的 Compose 数据库回归入口稳定可发现。

## 发现并修复的问题

首版账本实现将建表 SQL 以多行参数传给 MySQL client。Compose 解析后的命令中 `mysql -e` 未获得完整参数，真实执行报 `mysql: option '-e' requires an argument`。

修复为每个 MySQL `-e` 调用使用单一 shell 参数，再以真实 Compose job 回归。没有通过跳过 migration job 或忽略退出码来掩盖该故障。

## 自动化测试与回归证据

```bash
docker compose -f manifest/docker/docker-compose.yml config
make test-migration-ledger
make verify
git diff --check
```

结果：

- 首次 migration 写入 5 条账本记录，五条摘要均符合 64 位小写十六进制 SHA-256 格式。
- 第二次 migration 对五个文件均输出 `already applied; checksum verified`，没有重复 DDL 或账本记录。
- 测试将临时副本中的首个 SQL 加入注释；job 以 `migration checksum mismatch: 20260810_document_index_generation.sql` 和退出码 `1` 拒绝执行。
- `make verify` 通过 Go 短测试、Portal TypeScript 类型检查和敏感 sink 静态门禁；`git diff --check` 通过。

## 角色协作结论

- Agent 架构：定义账本不变量、启动门禁和中断补偿语义。
- Golang/平台后端：保持 MySQL 为迁移正确性边界，落地 Compose job 与可重复 DDL 约束。
- 自动化测试：新增可重复的正向、幂等、计数与篡改负向回归。
- 前端：本阶段不变更用户可见契约或 Portal；前端类型检查作为跨栈回归门禁执行。

## 剩余风险与后续门禁

- 当前 Compose job 适用于本地/集成部署。生产环境应使用受管 secret、最小权限 migration service account、部署系统的互斥/leader 机制和不可变制品仓库；不能复用开发账号或只依赖 Compose 单实例。
- 历史 migration 一旦已进入账本，任何修复必须新增迁移，禁止修改原文件。
- 后续新增 migration 必须运行 `make test-migration-ledger`，并在阶段文档中记录版本、摘要验证与回滚/前滚策略。
