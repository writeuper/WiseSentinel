# 阶段 10：告警字段最小化

## 根因

阶段 7 已避免保存原始 Webhook body，但“整包脱敏”仍会保留未知 label/annotation。外部告警系统经常附带调试标签、用户标识、URL 参数或内部上下文；这些字段既不是 Ops 关联所必需，也不应成为长期数据或 Agent 输入。

## 企业级方案

采用 schema allowlist：只保存业务诊断所需的 label（`alertname`、`severity`、`service`、`namespace`、`cluster`、`environment`、`instance`、`job`）和 annotation（`summary`、`description`、`runbook_url`）。所有允许字段仍经过统一脱敏和长度限制。原始 body 只参与验签/幂等 hash，不进入事件表或模型。

## 落地

- 新增 `alertEventProjection` 与 `filterAlertFields`，统一构造 `ws_alert_event.payload_json` 的安全 schema。
- Common labels/annotations 和每条 alert 分别按 allowlist 过滤。
- receiver、group key、URL、版本、指纹和文本字段使用 `redact.Summary`；最终 JSON 再执行防御性 `redact.JSON`。
- 增加 `alert_projection_test.go`，使用 canary 验证未知 `token`、`password`、调试 annotation 和敏感 URL 参数不会进入投影，同时允许的诊断字段仍存在。

## 回归证据

```text
go test ./internal/gateway/handler ./internal/pkg/redact ./internal/repository
make verify
```

均通过。

## 遗留项

- allowlist 当前在代码中维护；下一步可改为受控配置并增加 schema 版本和变更审计。
- `runbook_url` 的主机允许列表、URL 出站访问策略和 webhook 网络来源限制仍需落实。
- 仍需在真实 Alertmanager/HTTP 集成环境采集数据库、日志和 Ops API 进行 canary 端到端测试。
