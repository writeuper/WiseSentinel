# 阶段 155：Ops 耗时口径修复与提交验证

## 结论

修复了 Ops 任务耗时在亚毫秒阶段被截断为 `0ms` 的可观测性缺陷。对已完成且实际耗时大于 0 的 queue、run、e2e 阶段，API 现在以最小 `1ms` 表示；缺少起止时间的阶段仍保持 `0`，避免把“未发生”误报成“已完成”。

## 根因与影响

`internal/agent/ops/agent.go` 原先直接使用 `time.Duration.Milliseconds()`。工具执行或本地模型路径小于 1ms 时会得到 0，导致任务详情与下游报表无法区分“未测量”和“亚毫秒完成”。该问题不影响任务状态机，但会污染平均耗时、阶段耗时和长尾分析。

## 修复与测试

- 新增 `positiveMillis`：正耗时向上保留为至少 `1ms`，非正耗时为 `0`。
- 新增 `TestBuildOpsTiming_PreservesSubMillisecondStages`。
- 新增 `TestBuildOpsTiming_LeavesMissingStagesZero`。
- `go test ./internal/agent/ops`：通过。
- `go test ./...`：通过。

## 真实耗时基线（此前已验证）

基于 130 条分层评测和真实用户路径：

| 场景 | P50 | P95 | 说明 |
|---|---:|---:|---|
| Ops 异步诊断 | 约 699ms | 约 775ms | 85/85 通过，工具证据与 Trace 一致 |
| Chat/RAG | 约 16.125s | 约 36.419s | 44/45，1 次模型 timeout 后重试成功 |
| 同步 Chat，4 请求/2 并发 | 约 7.12s | 约 17.58s | 成功率 100%，会话清理 4/4 |

这些是当前样本基线，不应解释为生产 SLO；生产环境应按模型、租户、路由、工具和 RAG 命中情况分桶统计，并持续采集 P50/P95/P99。

## 部署验证

尝试执行：

```bash
docker compose -f manifest/docker/docker-compose.yml up -d --build platform
```

构建在 `debian:bookworm-slim` 安装 `ca-certificates` 阶段失败，原因是当前 Docker 构建环境从 Debian 仓库收到 `invalid signature`。Go 编译步骤未报告代码错误；平台容器因此未能在本轮重建启动。建议在具备有效镜像仓库签名/缓存的 CI 节点重试，并在启动后重新执行一条真实 Ops 任务确认 `run_duration_ms >= 1`。
