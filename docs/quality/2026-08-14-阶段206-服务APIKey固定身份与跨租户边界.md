# 阶段 206：服务 API Key 固定身份与跨租户边界

## 面试缺口

原有认证只提供开发 API Key。生产环境会拒绝开发 Key，但没有可供内部自动化、Webhook 适配器或调度器使用的固定服务身份入口，无法证明“密钥认证成功后租户由身份决定，而不是由请求头决定”。

## 实现

新增可选服务 API Key 认证：

- 通过 `SERVICE_API_KEY`（或配置 `auth.service_api_key`）注入密钥；仓库不保存生产密钥；
- 通过 `SERVICE_API_TENANT_ID`、`SERVICE_API_USER_ID`、`SERVICE_API_ROLES` 绑定唯一服务主体；
- 服务 Key 使用常量时间比较；
- `X-Tenant-ID`、请求体或 URL 不能覆盖服务身份租户；
- 开发 API Key 仍只在非 production 环境可用；服务 Key 与开发 Key 分开治理。

相关配置位于 `manifest/config/config.yaml`，默认服务 Key 为空，因此未配置时不会开放新入口。

## 回归证据

```text
go test ./internal/gateway/middleware -count=1   PASS
```

覆盖：

1. 正确服务 Key 映射到配置的 tenant/user/roles，并忽略攻击者预置租户；
2. 错误或空 Key fail-closed；
3. 既有开发 Key production 禁用和 JWT tenant 绑定回归保持通过。

## 企业级边界与后续

本阶段是固定单服务主体的最小闭环，不宣称完整密钥中心能力。生产化仍需：密钥哈希存储、轮换/撤销、多个服务账号、细粒度 scope、审计与密钥泄露告警，以及跨租户资源级黑盒矩阵。未完成这些项前，服务 Key 不应被描述为完整 IAM/API Key 管理平台。
