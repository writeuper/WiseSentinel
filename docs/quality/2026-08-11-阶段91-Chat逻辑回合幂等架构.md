# 阶段 91：Chat 逻辑回合幂等架构

日期：2026-08-11

## 发现

当前 Chat / Chat SSE API 不接受 idempotency key。浏览器、代理或用户在网络超时后再次提交相同问题，会创建新的模型调用、工具调用、Trace 和会话消息；若未来开放 L2 写工具，重复提交会扩大为副作用风险。

阶段 90 的 session 删除围栏只解决“失效会话不能保留迟到历史”，不等于“同一用户意图最多执行一次”。Redis 锁不能承担该语义：锁可过期、进程可崩溃、跨实例状态不可审计。

## 推荐架构

为每一个用户可见回合引入可选但由 Portal 默认提供的 `Idempotency-Key` HTTP 头。键必须是高熵、长度受限的 opaque 值；服务端按 `(tenant_id, user_id, session_id, idempotency_key)` 唯一化，并以请求规范化哈希绑定 question、RAG/tool options 和已授权的 session generation。

建议新增 `ws_chat_turn`：

| 字段 | 用途 |
| --- | --- |
| tenant_id / user_id / session_id | 服务端身份与对象边界 |
| idempotency_key / request_hash | 唯一回合与防止同 key 改写请求 |
| session_generation | 防止删除/重建后的陈旧回合提交 |
| status / execution_token / lease_expires_at | `running` 的数据库 CAS 与过期领取 |
| safe_response_json / trace_id | 已脱敏、可重放的成功响应；不可存原始工具输入或 provider body |
| error_class / finished_at | 稳定失败分类和审计 |

```text
new key ──insert unique──> running ──CAS token──> succeeded
                               │                    │
                    retryable overload              └── replay safe projection
                               │
                     failed / uncertain ──> require new explicit intent
```

### 关键不变量

1. 同一 key、相同 hash：成功时返回同一安全投影，不再运行模型或工具；running 时返回稳定冲突/重试状态。
2. 同一 key、不同 hash：`409`，不得将另一个问题绑定到旧回合。
3. 删除 session 会递增 durable generation；旧 generation 的回合不得写入 history 或被重放。
4. `50304` 在尚未获得模型准入时可 CAS 为 `retryable`；任何已进入工具/模型执行的不确定失败不得自动重放。
5. SSE replay 先发 `connected`，再发保存的 citation / message，最后 `done`；没有保存成功绝不发送 `done`。
6. Trace、日志、turn 表和浏览器均不记录原始 idempotency 之外的敏感 prompt/tool payload；只存 hash、脱敏投影和稳定分类。

## 前后端契约

- Portal 每次用户主动发送生成一个 `crypto.randomUUID()`；同一逻辑回合的人工重试复用该 key，而新编辑、新会话和用户明确再次发送生成新 key。
- API 客户端通过 `Idempotency-Key` 传递，不将其作为 URL 或日志字段。
- 服务端把 key 限制为长度 36–128 的 URL-safe 字符；缺失 header 维持兼容，但在指标中按低基数 `idempotency=missing|provided` 统计。
- 返回需携带 `turn_id` 与 `replayed` 布尔值，前端只展示真实状态，不把 replay 误称为新增执行。

## 必须的实现与回归门禁

1. 先添加幂等迁移、schema、repository CAS 和 migration-ledger 测试；再开启 API 行为。
2. fake model/tool 竞争测试：同 key 并发 N 次只执行一次；不同租户或不同 user 不能共享结果。
3. 同 key hash 冲突、session deletion、lease 超期旧 token、重复 SSE replay、`50304` retryable 与 provider uncertain failure 分别覆盖。
4. 真实 HTTP：并发相同 key、断线后重连、成功 replay、精确清理 session/turn，且 Redis/DB/Trace 无 canary 泄露。
5. 仅在这些门禁完成后，才能将“重试不会重复执行”纳入用户或生产 SLO。

## 当前边界

本阶段是已审计的架构与测试契约，**未开启该能力**。当前线上仍应将客户端超时后的 Chat 重试视为可能重复执行；L2 工具继续 fail-closed，不受影响。
