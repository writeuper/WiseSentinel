# 阶段 11：敏感 Sink 静态门禁

## 根因

运行时脱敏和单元测试可以验证已覆盖路径，但新功能可能再次把 `req.Input`、`argumentsInJSON`、`req.Query` 或 `err.Error()` 直接传给日志。此类回归通常在代码评审中不易察觉，且泄露发生在运行时。

## 企业级方案

采用“静态高信号守卫 + 运行时语义测试”的组合：静态规则只阻断已知高风险变量进入已知 GoFrame 日志 sink；运行时 canary 测试继续验证 JSON/文本及持久化投影。规则明确允许 `redact.Summary` 与 `diagnosticSummary`，避免把安全包装误报为违规。

## 落地

- 新增 `scripts/check_sensitive_sinks.sh`，扫描 `internal/toolkit`、`internal/agent`、`internal/rag` 和 `internal/gateway`。
- 阻断原始工具入参、模型工具 arguments、用户 query、错误文本直接传入 `g.Log().Infof/Warningf/Errorf`。
- 新增 `make test-sensitive-sinks`，并将其纳入 `make verify`。

## 回归证据

```text
make test-sensitive-sinks
make verify
```

均通过。

## 遗留项

- 该规则是有意收窄的 grep 守卫，不能替代 Go AST/semgrep 的跨行、跨包数据流分析。
- Trace repository、数据库 DTO、HTTP response 与前端展示 sink 仍需逐步增加专用静态规则和真实集成 canary。
- CI 环境必须确保 `rg` 可用；若迁移到极简构建镜像，需要把 ripgrep 固化为构建依赖或改用 AST 实现。
