# 阶段 102：Chat Trace 可诊断闭环

日期：2026-08-12

## 用户风险与根因

阶段 99 已让 Chat 回答显示短 Trace ID，也让后端持久化同步/SSE 的 RAG 与工具步骤；但 Chat 用户无法直接查看其回合的受控详情。真实 OnCall 在遇到长尾、无 citation、RAG empty 或工具失败时，需要离开当前用户旅程、转到 Ops 页面才能尝试排查，且不能确认结果来自同一回合。诊断证据虽存在，但未形成最小可用闭环。

## 企业级方案与取舍

推荐采用 **Trace ID 深链接 + 服务端对象级授权 + 脱敏投影**：

1. Chat 仅渲染当前浏览器新创建回答返回的 opaque Trace ID，不枚举或缓存全租户 Trace。
2. 新的只读详情页只能调用现有 `GET /traces/{trace_id}`；后端继续按 tenant、资源 owner 判定，只有同租户 `sre_admin` / `platform_admin` 可跨用户读取。
3. 不存在与无权限均返回 `40401`，避免成为 Trace 枚举侧信道；前端也以统一“Trace 不存在或无权访问”表达。
4. 页面只显示服务端已经脱敏的 trace/step 摘要、状态和时延，禁止在浏览器复原 prompt、原始工具载荷、provider body、Token 或 Cookie。

替代方案是仅在 Chat 气泡内内联所有步骤，或新增全局 Trace 搜索。前者会使会话 UI 混入大体量敏感诊断数据，后者需要额外的权限过滤、分页、审计、保留期和查询风控；本阶段不扩大攻击面，采用按已知 ID 的最小闭环。

## 角色协作与落地

| 角色 | 结论与实现 |
| --- | --- |
| Agent 架构师 | 定义“可诊断不等于可枚举”边界：深链接与 404 隐藏策略复用服务端 owner/RBAC 控制，不把 Trace ID 当作授权凭据。 |
| Golang 后端工程师 | 复核现有 Trace repository tenant filter、`canReadOwnedResource` 以及管理员跨用户读取语义；本轮无需新增后端 API、迁移或放宽权限。 |
| 前端工程师 | 新增懒加载 `Trace` 页面，展示状态、Agent 类型、开始/结束、总耗时和可折叠步骤；Chat 的短 Trace ID 改为详情链接。非法 ID 在浏览器侧拒绝请求，404 与无权统一处理。 |

## 剩余风险与下一阶段门禁

1. 当前 Trace 详情是按已知 ID 读取，尚无经权限、保留期和审计治理的列表/搜索能力；不能通过猜测 ID 用作运营检索。
2. Trace 摘要虽由服务端脱敏，但仍应持续用 canary 覆盖新工具、RAG 和 provider 错误投影；前端不能把摘要当作原始证据。
3. Trace 只改善诊断闭环，未改变阶段 98–100 的模型长尾、RAG 小样本评测、生产流量为零和 798KB 主 bundle 告警。上线前仍需经授权的脱敏流量/影子流量、按模型 profile 的阶梯压测，以及 100+ 人工复核 RAG 标注集。
