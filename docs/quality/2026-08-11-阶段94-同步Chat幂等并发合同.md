# 阶段 94：同步 Chat 幂等并发合同

日期：2026-08-11

## 风险

顺序“重复提交”只能验证缓存重放，无法证明多个平台实例同时收到相同请求时数据库唯一约束和 token CAS 真的阻止双执行。

## 自动化合同

`run_chat_idempotency_contract.py` 新增 `concurrent` 场景：对同一受控 session、同一 `Idempotency-Key` 通过 barrier 同时提交两次同步 Chat；随后再顺序重放一次并精确删除 session。

允许的响应类别只有：

- 一个请求成功、另一个 `40901` conflict；或
- 在极短时间内首个请求已经完成时，两个请求均成功但第二个为安全重放。

无论调度如何，模型 `ws_model_calls_total` 差量必须为 1。任何其他 HTTP 类别、两次模型调用或不可清理 session 都是合同失败。

## 真实结果

```json
{
  "model_calls_delta": 1.0,
  "outcome": "idempotency_concurrent_success",
  "request_outcomes": ["conflict", "success"]
}
```

这证明当前开发/集成环境中的两个并发 HTTP 请求通过 MySQL claim 只有一个模型执行者。结果不外推为生产容量或跨区域数据库 SLA。

## 边界

该合同只覆盖同步 Chat。SSE 未接受 idempotency key，L2 工具继续 fail-closed；没有 event journal、lease reclaim 与 generation CAS 时，流式断线重连仍不可宣称不重复执行。
