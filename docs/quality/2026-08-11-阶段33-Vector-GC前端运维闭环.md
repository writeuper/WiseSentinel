# 阶段 33：Vector GC 前端运维闭环

## 背景与风险

阶段 32 已提供 tenant-scoped dead-letter 诊断、审批申请和双人批准的后端契约，但 Portal 没有入口。管理员会被迫查询数据库或手工调用 API，容易遗漏审批前提，且不利于审计链路的日常使用。

前端必须是后端安全边界的展示与操作客户端，不能将本地角色、按钮隐藏或浏览器状态作为授权来源。

## 设计与实现

- 新增 `/vector-gc` 受控路由和导航，仅 `sre_admin|platform_admin` 可见；`RoleRoute` 仍作为 UX defense-in-depth，后端 `/api/v1/admin/*` RBAC 为最终权威。
- 新增“向量清理运维”页面：
  - 默认查看 `dead`，可按任务状态筛选和刷新；
  - 表格只显示 doc ID、target key/type、状态、尝试次数、下次重试和后端已脱敏的错误摘要；不显示 execution token、原始 Milvus expression 或敏感 payload；
  - 仅 `dead` 行显示“申请重驱”，其他状态明确为“无需人工操作”；
  - 二次确认 Modal 要求原因、显示精确 target，并明确说明操作须由另一管理员审批后才会入队。
- API client/types 与阶段 32 契约同步：`GET /admin/vector-gc/tasks` 与 `POST .../redrive`，path 参数通过 `encodeURIComponent` 编码。

## 安全与可访问性验收

1. 未认证用户被路由至登录页；operator/viewer 直达 `/vector-gc` 显示 403 UX，后端也会拒绝。
2. Modal 不声称已执行删除；成功提示的是 approval ID 和 pending 状态。
3. 原因字段为必填、长度受限；按钮、Tag、Table 与标准 Ant Design 语义组件支持键盘焦点与屏幕阅读器基础语义。
4. 宽表启用横向滚动，避免窄屏截断目标、状态和操作。

## 回归证据

```bash
cd portal
./node_modules/.bin/tsc -b --pretty false
./node_modules/.bin/vite build
```

结果：通过。Vite 仅报告现有主 bundle 大于 500 KiB 的性能告警，未阻断构建；后续可按路由动态加载管理页以优化首屏。

## 后续

- 审批中心目前能以 `vector_gc_redrive` 类型展示 pending approval，但没有解析该审批的精确 target（后端也不向前端返回 payload）；可在后续增加最小、脱敏的 approval target projection。
- 需要在部署环境对接 Alertmanager receiver，并针对告警中的 dead-letter count 进行 Portal 到 `/vector-gc` 的深链联动。
