# 阶段 51：Chat 流式背压与部分回答保护

日期：2026-08-11

## 缺陷根因

Chat stream 的事件 channel 容量为 64，原 `send` 在满时走 `default`，静默丢弃 message、error 甚至 done。慢 SSE 客户端或模型快速产生超过 64 chunk 时，用户会收到截断回答；handler 随后仍把已截断内容写入会话历史，污染下一轮 Agent 上下文。

同时 `Recv()` 的非 EOF provider 错误此前会被无条件转成 done，客户端误以为是干净完成。

## 企业级方案与实现

采用可取消背压而非静默丢弃：

- `chatStreamReader.send` 在消费者慢时阻塞，直到事件入队或 reader/context 被关闭；断开连接能解除阻塞，避免 goroutine 泄漏。
- 保留有界 channel，但队列满成为上游节流信号；消息顺序和 done/error 不再因容量丢失。
- 区分 `io.EOF` 与实际 provider receive error；后者输出稳定 SSE `error` 后才发送 done，服务端日志不回显原始 provider 错误。
- SSE handler 收到 error 或 request context 已取消时不写入 user/assistant message，不再持久化部分回答或更新会话标题。

## 剩余风险

- 当前 HTTP 验证覆盖确定性时间工具；模型 provider 非 EOF 注入为单元级错误语义验证，后续应接入可控 fake provider 做 SSE 端到端中断回归。
- 背压会把慢客户端的消费速度传导至模型 stream；生产需要增加每连接最大持续时间、最大 chunk/字节预算、客户端断开指标和高水位告警，避免慢客户端占用长期连接。
