# 阶段 13：前端身份失败收敛

## 根因

AuthContext 会从 localStorage 恢复 `ws_roles`，并在 `/me` 调用失败时继续使用该缓存。localStorage 可被用户修改，且 token 失效后仍可能让 Portal 显示高权限入口/路由，虽然 API 会拒绝请求，但最小权限体验被破坏。

## 企业级方案

角色和租户身份只能由服务端 `/me` 确认。客户端缓存仅作非授权性提示，不能参与授权判断。身份暂时无法确认时角色收敛为零权限；明确的 401/403 立即清理会话并回到登录流程，网络故障则保留 token 但仍不展示受控能力。

## 落地

- AuthContext 初始 roles 改为空数组，不再从 `ws_roles` 恢复。
- `/me` 刷新失败时清空角色缓存；401/403 同时清理 token、用户名和 tenant 状态。
- 登录后无法读取 `/me` 时回滚刚写入的 token 和身份状态，并将错误交给登录页处理。
- 手动 refresh 遇到身份失败也遵循相同的最小权限策略。

## 回归证据

```text
make typecheck-frontend
make verify
```

均通过。

## 遗留项

- 当前缺少 React 测试运行器；应补充 `/me` 401、网络失败、localStorage 注入管理员角色、登录后身份读取失败的交互测试。
- `username`/`tenantId` 仍可在首次渲染短暂显示缓存值，但不参与前端授权；后续可引入显式 `identityState=loading|verified|failed` 以改善 UX。
- API 仍是唯一安全边界，前端状态不能被视作权限证明。
