# 阶段 93：会话幂等记录生命周期

日期：2026-08-11

## 问题

阶段 92 引入的 `ws_chat_turn` 能阻止同步 Chat 重复执行，但删除 session 时仅清除了 Redis 历史。已删除 session 不能再经 API 重放，但其幂等响应投影与 key 会无限保留，违反最小化保留原则，也会增加运维表膨胀。

## 实现

将 session 的 durable 删除边界升级为单个 MySQL 事务：

1. 以 `tenant_id + session_id + status=1` CAS 将 `ws_session` 置为 inactive；
2. 只有该 CAS 成功时，删除相同 tenant/session 的全部 `ws_chat_turn`；
3. 事务提交后才精确删除 Redis message key。

这避免两类错误交错：

- 先删 turn、后 session CAS 失败，会让仍活跃会话丢失重放保护；
- 先删 session、异步删 turn，会把已删除用户数据留在数据库中。

Redis 故障沿用既有 fail-closed 语义：数据库访问围栏已生效，API 不会重新暴露 session；错误会返回而不是静默假成功。

## 剩余风险

此清理仅覆盖同步 Chat turn。SSE event journal、running-turn lease reclaim、session generation 和跨副本断线重放尚未实施，不能将流式客户端重试称为无重复执行。
