# 阶段 72：模型容量保护与过载契约

日期：2026-08-11

## 问题与根因

阶段 71 的 5 并发真实 Chat 探测曾出现模型总预算耗尽后的 504。继续审计发现两个更深层的问题：

1. `ModelRouter.ChatModel` 每个请求都会构造新的 OpenAI 适配器；原本“每实例”的熔断器不能跨请求累计，因此并不是真正的 profile/provider 熔断。
2. 调用路径没有模型并发准入。并发请求会直接打向同一上游，最终由供应商长尾随机决定失败者。单纯提高 timeout 会扩大资源占用，不能解决饱和。

首次落地容量令牌后，Eino ReAct 将子模型的 `AppError` 格式化为 `NodeRunError` 且未保留 `Unwrap`，导致 API 一度返回 500。该问题被真实压测发现，不能以“内部错误”掩盖可重试过载。

## 企业级方案与实现

- 模型 profile 运行态独立于请求实例：工具绑定副本与每次路由获取的模型实例共享同一份熔断状态和 admission channel。
- `chat_fast.max_concurrent: 3` 启用非阻塞有界准入。槽位不足时立即返回稳定 `50304 / 模型服务当前繁忙，请稍后重试`，避免继续压垮上游并转化为不透明 timeout。
- 非流式调用在整个生成（包括重试）期间持有槽位；流式调用从握手成功持有至流关闭。失败请求都会释放槽位。
- `ws_model_calls_total` 与时延指标新增受控 `overloaded` outcome；不携带模型名、租户、提示词、URL 或上游错误正文。
- Chat Agent 在 Eino 丢失错误链时仅依据精确、稳定的 AppError 文案恢复过载语义，其他错误仍走原有失败路径。
- 并发压测脚本读取统一 API envelope 的稳定业务码，并继续只写入聚合类别；同时修正了 session 删除后 `api_40401` 的 cleanup 验证。

## 验收证据

| 检查 | 结果 |
| --- | --- |
| 模型/Chat/观测 Go 测试 | 通过 |
| Python 评测与并发脚本测试 | 10/10 通过 |
| 全量真实评测 | 25/25（100%） |
| 路由准确率 / 必需工具成功率 | 100% / 25/25（100%） |
| 关键词原始命中 | 61/71（85.9%，各用例达阈值） |
| 全量评测 P50 / P95 | 114ms / 13.798s |
| Chat 10 请求 / 2 并发 | 10/10 成功，cleanup 10/10 verified（P95 17.781s） |
| Chat 5 请求 / 5 并发 | 3 成功、2 个 `api_50304`，cleanup 5/5 verified，无 500/504 |

该 5 并发结果代表容量保护正确生效，而不是“5 并发任务完成率已达标”。平台目前可将超出 chat profile 已验证容量的请求明确、快速地拒绝；客户端/Portal 应按用户交互幂等策略对 50304 做退避重试或排队提示。

## 剩余风险与下一阶段

- 当前准入是单进程、单 profile 的固定上限；多副本部署需使用每副本配额加全局供应商预算/租户公平配额，或采用可观测的分布式 admission。
- 需要定义 `Retry-After`、前端重试次数/抖动、队列等待上限和产品级时延 SLO，再进行 2→5→10→目标容量的阶梯压测。
- Ops 的 plan/exec profile 尚未配置独立并发上限；应依据供应商配额和业务优先级单独设置，不能默认与 Chat 共用无限容量。
- 未发现真实生产用户或生产流量；本结果仅适用于真实模型依赖的开发/集成环境。

普通 L2 写工具继续 fail-closed，直到 durable intent、command vault、outbox、SoD 和可恢复的幂等执行器完整落地。
