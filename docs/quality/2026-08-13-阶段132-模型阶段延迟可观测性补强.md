# 阶段 132：模型阶段延迟可观测性补强

## 背景

此前质量报告能输出 Agent 端到端平均耗时和 RAG 检索 P95，但无法直接回答长尾究竟来自 RAG、模型生成还是工具执行。上一轮真实评测中出现 27–42 秒级 Chat/RAG 长尾，需要拆解阶段耗时后再决定优化方向。

## 变更

增强 `scripts/report_agent_quality_metrics.py`：

- 解析 `ws_model_call_duration_seconds` Histogram；
- 输出模型调用总样本、成功样本、超时样本；
- 输出成功模型调用均值和 P95；
- 明确 P95 是 Histogram finite bucket 上界，不伪装成精确 percentile；
- 保持 provider、模型名、租户、Prompt 和错误原文不进入报告；
- 增加成功/超时分离的解析单测。

## 当前观测

当前进程 Prometheus 样本：

- RAG 检索样本：92；成功 90；错误 2；
- RAG 成功检索均值：190.577 ms；P95：250 ms（桶上界）；
- 模型生成样本：95；成功 92；超时 1；其余为取消等非成功终态；
- 模型成功生成均值：8,435.256 ms；P95：20,000 ms（桶上界）；
- 持久化 Trace 全部终态平均耗时：7,413.05 ms；成功 Trace 平均：7,227.96 ms；
- 平均 Trace 步数：2.939。

## 结论

当前 RAG 检索本身不是主要长尾来源；端到端长尾更可能由模型生成、模型重试或多步 Agent 编排造成。模型阶段 P95 仍是本进程窗口观测，不能跨重启直接累加，也不能替代 Prometheus recording rule 的生产窗口统计。

## 后续优化建议

1. 按 `operation` 分别建立模型生成、流式握手、流式完成的生产 P95/P99 recording rule；
2. 将模型总预算、重试次数、Agent 最大迭代次数纳入同一 SLO 看板；
3. 对 RAG/工具快速成功但模型超时的 Trace 建立 Bad Case 聚合，优先优化 Prompt 长度、工具返回摘要和 ReAct 最大步数；
4. 评测报告同时保留业务质量通过率和基础设施失败率，避免模型长尾被误计为路由或工具准确率问题。
