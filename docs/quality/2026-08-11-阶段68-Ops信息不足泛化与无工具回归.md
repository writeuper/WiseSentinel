# 阶段 68：Ops 信息不足泛化与无工具回归

日期：2026-08-11

## 缺陷发现

`BAD-001` 只覆盖精确文本“系统有点慢帮我看看”。新增同义真实用例 `BAD-002`（“系统很慢请帮忙看看”）发现平台会落入通用 Plan-Execute 图：forbidden tool 被调用、关键词 0/3、端到端 38.208s。问题不在模型不可用，而是信息不足识别使用精确字符串；Agent 执行和 Handler 的安全响应也各自维护重复规则。

## 企业级方案

没有服务、时间窗、异常类型或可验证证据的请求不得触发日志、指标、告警或部署读取。澄清策略应是共享领域契约：先识别 trace、告警、日志、指标、错误码、超时、数据库、发布和限流等具体证据；无具体证据的慢/卡/异常/帮忙等模糊请求返回引导性澄清。该规则是保守入口保护，不替代复杂语义分类或人工确认。

## 落地

- 新增 `domain.NeedsOpsClarification`，由 Ops Agent 与 API 安全响应共同使用。
- 将 `BAD-002` 纳入冻结评测，并禁止所有当前只读诊断工具。
- 新增正反单元用例，确保 500、firing、延迟和 trace 等具体请求不会被误拒，而两种模糊“慢”句式必须澄清。

## 回归

```bash
go test ./internal/domain ./internal/agent/ops ./internal/gateway/handler -count=1 -v
python3 scripts/run_agent_eval.py ... --case BAD-002
```

均通过。修复后的真实 `BAD-002`：route=ops、实际工具为空、forbidden 0/5、关键词 3/3、252ms。服务重新部署且 readiness 通过。

## 剩余风险

规则仍是中英文关键词启发式，可能对未覆盖的模糊表达出现漏判或对短但具体的新服务名过度澄清。后续应建立人工标注的“可行动/需澄清”意图集，按语言、业务域、租户和时间窗评估 precision/recall；任何扩展都必须保留无工具断言和正向不误拒回归。
