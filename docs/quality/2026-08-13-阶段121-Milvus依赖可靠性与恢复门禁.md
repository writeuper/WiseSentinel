# 阶段 121：Milvus 依赖可靠性与恢复门禁

## 发现

本轮启动时 `/health/ready` 再次报告 `milvus=down`。容器检查显示 `milvus-standalone` 已退出（exit 1、OOM=false），日志包含 etcd lease 不存在、组件连接超时、TSO clock offset 和 `Proxy disconnected from etcd, process will exit`。这不是业务 Agent 代码或 RAG 查询断言问题，而是向量数据库依赖在异常状态下退出，且原 Compose 配置没有自动重启和健康依赖围栏。

## 修复

在 `manifest/docker/docker-compose.yml` 中：

- 为 etcd、MinIO、Milvus 增加 `restart: unless-stopped`；
- Milvus 改为等待 etcd、MinIO `service_healthy` 后启动；
- platform 和 Attu 改为等待 Milvus `service_healthy`，不再只等待进程启动；
- 新增 `scripts/test_compose_resilience.py`，以 `docker compose config --format json` 校验上述不变量。

## 先失败后通过

修复前新增门禁得到 3 个失败：

- etcd/Milvus 无 restart policy；
- Milvus 仅依赖 `service_started`；
- platform 仅依赖 `service_started`。

修复后：

```text
Ran 3 tests ... OK
docker compose ... config: success
```

## 运行态验证

- 仅重建 Milvus 依赖栈，未删除数据卷；
- etcd、MinIO 健康后 Milvus 从 `starting` 到 `healthy` 约 8 秒；
- Milvus `:9091/healthz` 返回 `OK`，平台 `/health/ready` 返回 `ready=true`；
- 真实 RAG-001：1/1 通过，工具命中 1/1、关键词 4/4，端到端 11.617 秒；
- 通过 `docker kill --signal=KILL` 验证容器进入 exited，随后显式 `docker start` 约 8 秒恢复 healthy，平台 readiness 恢复。

## Docker 语义边界

`unless-stopped` 用于非计划的进程/容器退出；Docker CLI 显式 `stop`/`kill` 属于人工停止，Docker 可能不自动重启，这是平台运行时语义，不应当被测试报告为自动恢复成功。若生产需要人工停止后仍自动拉起，应由编排系统或运维控制面明确执行恢复，而不是依赖该策略。

## 剩余风险

1. etcd 日志仍显示 compaction 和 linearizable read 偶发慢、时钟偏移风险；生产应监控节点时钟同步、磁盘 I/O、etcd 延迟和 Milvus 组件会话。
2. `restart` 只能提高容器级恢复能力，不能修复 etcd 数据损坏、时钟跳变或宿主机资源不足；需要告警、重试预算和人工介入 Runbook。
3. 前端主 bundle 仍有约 798 KB 构建警告，后续应做动态分包。
