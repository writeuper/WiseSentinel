# 阶段 210：服务 API Key 细粒度 Scope 门禁

## 面试缺口

阶段 206 的服务 API Key 已固定绑定 tenant/user/roles，但仅依赖角色仍然过粗：同一服务身份若拥有 `operator` 或 `sre_admin`，无法区分它是否被允许执行 Ops、审批、配置激活或知识库写操作。

## 实现

- 服务 API Key 认证上下文新增 `auth_method=service_api_key` 和显式 scopes；
- 支持 `SERVICE_API_SCOPES` 或 `auth.service_scopes` 配置，默认仅为 `chat:invoke`；
- RBAC 对服务身份增加路由级 scope 门禁：
  - Ops：`ops:read` / `ops:execute`
  - Agent 配置：`agent_config:read` / `agent_config:write`
  - Knowledge：`knowledge:read` / `knowledge:write`
  - Approval：`approval:read` / `approval:decide`
  - Trace：`trace:read`
- 缺少 scope 时 fail-closed 返回 Forbidden；JWT 用户仍走原有角色 RBAC，不要求服务 scope。

## 验证

专项测试覆盖 scope 精确匹配、缺少 scope、路由映射、服务身份上下文以及 JWT 兼容行为。服务 Key 的 tenant 仍由服务配置绑定，不能由请求头覆盖。

## 剩余风险

当前仍是单固定服务主体配置，不是完整 API Key Registry；尚未实现密钥哈希存储、轮换、撤销、多个服务账号、scope 管理 API 和泄露告警。生产上线前必须接入 Secret Manager/IdP，并做资源级跨租户黑盒矩阵。
