# 阶段 81：跨 Profile 模型预算与 Ops 假成功修复

日期：2026-08-11

## 问题与根因

Chat、Ops planner、Ops executor 和 replanner 默认解析为同一模型部署/凭据，但此前运行态按 Profile 创建。即使 Chat 设置了并发上限，Ops 可同时建立自己的 admission channel，整体仍可能超过同一供应商的额度。

同时，Ops Plan/Execute 图收到模型事件错误时会记录 detail 后继续；没有最终文本时会构造兜底“成功”结论。这会把模型过载或图失败误称为无证据的成功诊断。

## 企业级修复

- Model Router 以 `provider + model + base URL + credential fingerprint` 建立共享运行态。API key 只参与 SHA-256 指纹，不进入 map key 的明文、日志或指标。
- 新增 `models.admission.max_concurrent: 3`，对解析到同一部署/凭据范围的 Chat、Ops plan/exec/replan 共同生效；保留 profile 层配置仅作为没有全局预算时的兼容回退。
- Ops 遇到模型/图事件错误立即终止执行；识别到稳定过载文案时返回 `50304`，而不是生成无证据兜底成功。

## 验证

- Router 确定性并发单测以同一个 fake 上游阻塞 Chat 调用，再由 Ops Profile 模型调用；Ops 收到 `ErrModelOverloaded`，证明不是仅比较指针而是真正共用 admission budget。凭据不同仍隔离。
- Ops 单测确认 typed 和 Graph 格式化的 overload 都可识别并归一为 `ErrModelOverloaded`，普通错误保持原错误，不会误识别。
- Chat、Ops、model、handler 相关 Go 测试通过；后端完成重建部署并 readiness 通过。
- 真实普通 Ops 模型请求（非 focused-tool 路径）在共享预算配置下返回成功，证明运行态变更未破坏正常 Ops 执行。

## 剩余风险

真实模型的首 token 时序不可控，无法用当前外部供应商压测稳定断言“某一 Profile 必定被拒绝”。跨 Profile 总预算的共享关系已有确定性单测；生产级验证应增加可控假模型/延迟注入集成测试，固定 3 个 Chat 占槽后验证 Ops 返回 50304，并验证任务状态为 failed 而非 success。
