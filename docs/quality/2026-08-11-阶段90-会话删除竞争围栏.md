# 阶段 90：会话删除竞争围栏

日期：2026-08-11

## 问题与根因

Chat 在生成开始前检查 session，但模型调用期间用户可在另一请求、另一实例中删除会话。此前 `AppendMessages` 不再核验数据库状态，晚到生成可能在 Redis 保留已删除 session 的消息窗口；首轮 title 更新也可能修改已失效记录。

这会造成 Redis 无效数据滞留、运维诊断混淆，并使“删除即停止保留”这一用户预期不完整。

## 本阶段实现

数据库 `ws_session.status` 是删除的持久化权威：`DeleteSession` 先将其转为 inactive，再删除对应 Redis key。

- `AppendMessages` 在 Redis 写入前与 `EXPIRE` 后均检查 session 是否 active。
- 若写入后发现删除竞争获胜，仅删除该 `(tenant_id, session_id)` 的 Redis key 并返回稳定 not-found 结果。
- `UpdateTitle` 增加 `status=1` 条件，不能复写已删除会话。
- SSE handler 将会话保存失败映射为受控 `error` 而非 `done`，Portal 会显示未完成状态。
- 自动化 SSE 合同新增 `delete-race`：收到 `connected` 后立即删除 session，要求无 `done` 且 history 不可读。

该策略的关键交错如下：

```text
生成写入前检查 ── active ── Redis 写入 ── 写后检查
     │                                    │
删除：DB status=inactive ── Redis DEL ────┴──> 精确 DEL + 不完成
```

若删除发生在写后检查之前，由写后检查清理；若删除发生在检查之后，删除操作自身清理。数据库或 Redis 不可用仍会返回失败，不吞掉错误。

## 边界与后续架构

本阶段解决了 Redis 历史延迟写入的清理竞争，但不是跨服务的请求级“恰好一次”协议。生产多副本仍需把 session generation / turn idempotency key 持久化，并以 generation CAS 绑定 `start → model → persist`；客户端超时后重试还必须复用同一 logical turn，避免模型和工具执行重复。

此外，应用当前可选 MCP 时间服务在冷启动时可等待约 12 秒后降级。应将其拆出关键启动路径，或设独立启动预算、降级指标和冷启动 SLO。
