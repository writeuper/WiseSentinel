# 阶段 22：Embedding 成功响应预算

## 根因

阶段 21 已验证 DashScope 的成功响应结构，但仍以 `io.ReadAll` 无上限读取整个 HTTP body。外部 embedding 服务或中间代理即使返回 HTTP 2xx，也可能返回异常大的 JSON 负载；这会在线程内造成不受控内存分配、GC 压力和 RAG 索引 Worker 可用性下降。

## 企业级方案

将外部成功响应作为有资源预算的不可信输入。响应预算应在 JSON 解析之前、流式读取期间强制执行；上限取可审计的配置，越限返回稳定错误且不尝试局部解析。HTTP 失败路径继续不读取 body，避免错误内容泄露。相比仅依据 `Content-Length` 的方案，受限读取可覆盖 chunked 传输和伪造/缺失的长度头。

本阶段选择按 embedding profile 配置 `max_response_bytes`，默认 4 MiB。该值覆盖常规批量向量 JSON 响应，同时为服务端、模型和调用方留下后续按租户/模型细分的空间。

## 落地

- `DashScopeEmbedder` 增加 `maxResponseBytes` 与 `responseLimit()`，兼容未设置该字段的既有实例并安全回退至 4 MiB 默认值。
- `models.profiles.embedding_default.max_response_bytes` 配置为 `4194304`。
- 成功响应由 `readEmbeddingResponse` 通过 `io.LimitReader(max+1)` 读取；实际字节数超过上限时返回 `dashscope embedding response exceeds configured size limit`，不进入 JSON 解析。
- 保留阶段 20 的非 2xx 最小披露策略：失败状态在读取 response body 前即终止。
- 新增受控 HTTP 回归：成功 body 超限必须拒绝；恰好等于配置上限的合法响应必须接受。

## 回归证据

```text
gofmt -w internal/rag/embedder/dashscope.go internal/rag/embedder/dashscope_test.go
go test ./internal/rag/embedder
make verify
```

均通过。`make verify` 覆盖 Go 短测试、Portal TypeScript 编译和敏感 sink 静态门禁。

## 遗留项

- 响应大小预算不限制 JSON 解码后的数组/嵌套对象复杂度；后续应增加每请求输入数量、单向量维度和总浮点数预算。
- `float32` 接受的 NaN/Inf 数值仍需显式拒绝，避免污染向量检索与索引。
- 尚需在真实 Milvus 索引集成测试中验证该失败不会把 Index Task 标为成功或留下部分向量。
