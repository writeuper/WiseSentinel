# 阶段 71：评测身份治理与并发容量复验

日期：2026-08-11

## 问题与根因

评测和并发脚本曾把 `X-Tenant-ID` 参数描述为“隔离租户”。但开发 API Key 在服务端被固定绑定为 `default`；认证中间件会覆盖该 Header。因此，脚本可在 `default` 租户执行，却在工件和说明中错误宣称使用了另一个租户。

这不是已发现的越权漏洞：实际无破坏验证表明，携带开发 API Key 与任意攻击者租户 Header 调用 `/me` 时，返回的仍是 `default`。问题是测试身份治理不严谨，可能误导测试数据隔离和结果归属。

## 修复

- `run_agent_eval.py` 与 `run_concurrent_chat_load.py` 均先调用 `/me`，将请求的测试租户与认证身份中的 `tenant_id` 严格比较；不匹配时以稳定错误 `requested tenant does not match authenticated test identity` 在执行前失败。
- 两个脚本支持预先配置的 `--bearer-token`，优先于开发 API Key。企业环境要使用独立测试租户，必须预配带该 tenant claim 的受限测试 JWT/API credential，不能通过 Header 伪装，也不能由脚本构造 JWT。
- 知识评测的默认租户调整为 `default`；取消 ROUTE-004 临时改写 tenant。测试隔离改为唯一 marker/document ID，并继续在成功与失败路径精确删除并验证资源。
- 增加脚本单元测试，覆盖认证租户匹配与不匹配；真实负向验证确认不匹配会在任何评测前退出。

## 容量结论与上线门禁

当前真实上游模型在该开发/集成环境中可稳定支撑本次 2 并发基线；5 并发出现长尾超时，不能将 5 并发、100% 成功率或 30 秒以内 P95 声称为已验证 SLA。

生产化前应由架构/后端实施并验证：按模型 profile 的有界准入队列（队列上限、等待预算、显式 overload 响应）、租户公平配额、排队/执行时延与拒绝原因指标、压测阶梯 2→5→10→目标容量，以及按模型供应商/版本和时间窗拆分的 SLO。前端应将可重试的容量拒绝与真实模型超时区分展示，并保留 trace/请求标识入口。

普通 L2 写工具仍保持 fail-closed。架构、后端、前端联合复审确认它尚未具备 durable intent、加密 command vault、outbox、职责分离、幂等恢复 Worker；因此不得把审批“已通过”表述为工具已经执行。

## 生产流量与指标口径

本轮使用根目录 `.env` 的真实模型依赖和本地运行服务，但没有发现或接入真实业务用户、生产租户或生产流量的证据。所有结论仅适用于开发/集成环境。评测集当前为 25 个冻结场景；RAG 文档/Chunk/向量规模与生产用户规模必须从受控生产遥测/数据目录按租户和时间窗另行采集，不能由本地评测外推。
