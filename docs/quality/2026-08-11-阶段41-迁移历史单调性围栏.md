# 阶段 41：迁移历史单调性围栏

## 问题根因与影响

阶段 39 已验证账本中“当前制品包含的 migration”摘要，阶段 40 已使同一数据库上的 runner 串行。然而旧版本制品部署到已升级数据库时，旧制品不会遍历较新的账本记录，仍可能让 `platform` 启动。代码、数据模型与 Agent 任务状态机由此发生不受控的向后部署。

此风险会直接影响 Agent 平台中租户隔离、审批、RAG 代际和异步任务等数据库契约：数据库已经前移而应用代码回退时，单纯依靠服务健康检查无法证明兼容性。

## 企业级方案与选择

1. 只在 CI/CD 中限制发布顺序：必要但不充分，手工 Compose、紧急回滚和错误制品仍可能绕过。
2. 允许历史 SQL 被删除或改名：失去可审计的演进链，也无法可靠还原环境，未采用。
3. 以数据库迁移账本和当前制品双向比对：账本中每条历史 migration 都必须在当前 `/migrations` 制品内存在；采用。

该机制形成单调性不变量：数据库已应用迁移集合必须是当前部署制品迁移集合的子集。回滚必须走兼容代码、显式前滚 migration 或经过审查的恢复流程，不能用较旧制品直接覆盖。

## 落地实现

- `manifest/docker/migrate.sh` 在创建账本后读取所有已登记 migration。
- 若某条账本记录在 `/migrations` 中不存在，job 以
  `migration history is not present in deployment artifact: <name>` 退出。
- 检查在取得 execution lock、执行任何 SQL 和放行 `platform` 前完成。
- 现有同名摘要围栏、advisory lock 和 `service_completed_successfully` 启动门禁保持不变。

## 自动化回归

`scripts/test_migration_ledger.sh` 使用唯一的测试专用 migration 名称，精确插入一条账本记录，再运行真实 Compose job：

- 预期 job 非零退出且输出缺失历史诊断；
- 测试退出前仅删除本次创建的精确账本记录；
- 随后继续执行并发锁拒绝、摘要篡改拒绝和重复运行回归；
- 最终账本计数重新为当前五个真实 migration，证明测试未污染共享开发数据库。

没有通过忽略旧账本、自动删除生产历史或回退 schema 来制造启动成功。

## 验证证据

```bash
sh -n manifest/docker/migrate.sh
bash -n scripts/test_migration_ledger.sh
make test-migration-ledger
make verify
docker compose -f manifest/docker/docker-compose.yml config
git diff --check
```

结果：缺失制品历史的负向用例被拒绝；账本条目数保持为 5；并发、摘要篡改与重复执行回归通过。`make verify` 通过 Go 短测试、Portal TypeScript 类型检查和敏感 sink 静态门禁。

## 角色协作与后续门禁

- Agent 架构：定义数据库/制品迁移集合的单调性契约和回滚边界。
- Golang/平台后端：将契约落实在启动前的 MySQL migration runner 中，确保 MySQL 仍是权威状态。
- 自动化测试：以真实 Compose 数据库验证拒绝路径，并精确清理测试创建的记录。
- 前端：本阶段没有用户可见接口变更；继续以 TypeScript 门禁验证跨栈稳定性。

生产仍应有制品签名、不可变镜像、部署审批、受管 secret 和经过演练的恢复预案。新增 migration 不得删除或改名历史文件，并必须运行 `make test-migration-ledger`。
