# 阶段 14：Webhook 负载上限

## 根因

Alertmanager 签名中间件使用 `io.ReadAll(r.Body)` 读取完整未受信任请求。攻击者可发送超大 body，使应用在验签前消耗大量内存，形成拒绝服务风险。

## 企业级方案

在认证边界对原始请求使用有界读取：最多读取上限加一个字节以准确识别超限，超限立即返回 413；上限内字节保持原样，继续作为 HMAC 输入和后续幂等 event hash。默认上限 1 MiB，并提供受控配置/环境覆盖。

## 落地

- 新增 `readWebhookBody`，通过 `io.LimitReader` 读取 `max+1` 字节并返回明确的超限错误。
- `AlertmanagerSignature` 在验签前拒绝超限 payload，返回 `413 webhook payload too large`，不泄露验签或密钥信息。
- 配置新增 `webhook.alertmanager.max_body_bytes: 1048576`，环境变量为 `ALERTMANAGER_WEBHOOK_MAX_BODY_BYTES`。
- 新增边界测试，验证恰好等于上限的请求被接受、超出一字节被拒绝。

## 回归证据

```text
go test ./internal/gateway/middleware
make verify
```

均通过。

## 遗留项

- 最大 body 限制不能替代网关/WAF 的连接数、带宽、慢请求和来源网络策略。
- Alertmanager 实际部署的 payload 尺寸需纳入容量基线，调整上限需要变更审计。
- 仍需在 HTTP 集成环境断言 413 不进入 handler、不会写入告警表或创建 Ops task。
