# 阶段 15：限流计数完整性

## 根因

Redis 滑动窗口将毫秒时间戳同时作为 ZSET score 与 member。并发请求若落在同一毫秒，`ZADD` 会覆盖同一个 member，`ZCARD` 低于真实请求数，攻击者可利用高并发绕过配额。已签名的 Alertmanager Webhook 也未进入限流中间件。

## 企业级方案

滑动窗口使用时间戳作为 score、每次请求的唯一 ID 作为 member，保证计数与请求一一对应。外部 Webhook 在通过 HMAC 验签后纳入单独的 tenant 级配额，避免无效请求占用 Redis，也限制合法凭据被滥用时的下游 Agent 成本。

## 落地

- Lua 脚本新增唯一 member 参数，使用 `timestamp:UUID` 写入 ZSET。
- 新增 `rate_limit.webhook_per_minute`（默认 120），路径 `/internal/webhooks/alertmanager` 由验签后限流。
- Router 将 `RateLimit` 放在 `AlertmanagerSignature` 后、业务 handler 前。
- 新增回归测试：同一毫秒生成的 member 必须不同；签名 Webhook 必须解析到独立限流配置。

## 回归证据

```text
go test ./internal/gateway/middleware ./internal/gateway
make verify
```

均通过。

## 遗留项

- Redis 不可用时当前策略仍为 fail-open；对高成本 Agent/写操作应支持按路由配置的 fail-closed 或本地熔断降级。
- 需要真实 Redis 并发集成测试，证明同一毫秒 N 次 EVAL 后 ZCARD 和拒绝阈值准确。
- Webhook 限流以 tenant+anonymous 维度计数；若允许多个签名来源，应结合可信 source identity/证书进一步分桶。
