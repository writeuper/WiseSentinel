# 阶段 77：流式过载语义与容量回归

日期：2026-08-11

## 问题与根因

初次流式容量压测把存在 `done` 事件的响应算作成功，忽略了前序 `error`。真实指标显示 Stream admission 已产生 overload，但 Agent 会在已提交 SSE 响应后以通用错误文本发送，Portal 无法知道这是可在 2 秒后重试的 `50304`。

HTTP 流一旦写出 200/SSE headers 后不能改为 503 或添加 `Retry-After`，因此不能套用同步接口的错误表达方式。

## 企业级处理

- 流式模型过载在 SSE `error` event 中传输受控结构：`code=50304`、稳定 message、`retry_after_seconds=2`。未知上游错误仍仅发送固定通用文案，禁止泄露异常正文。
- Portal SSE parser 将该结构映射为 `ApiError`，复用 Chat 页既有“建议 2 秒后重试”提示。
- 压测判定改为：仅无 error 且收到 `done` 才是成功；`error(50304)` 即使随后收到 `done` 也必须统计为明确过载。
- 普通 HTTP Chat 仍使用 `503 + Retry-After`；SSE 使用事件内重试提示，这是协议提交时机导致的必要区别。

## 真实并发回归

10 个并发真实 SSE Chat：**3 个 `success_done`，7 个 `sse_50304_retry_2`**。没有通用 500、无业务码丢失。随后再发起单条 SSE 请求并收到 `done`，证明成功/过载流结束后容量令牌可再次获取。所有压测 session 均精确删除。

## 门禁

- Chat Agent 新增结构化流错误单测，确认未知错误不会泄露。
- Chat/handler/model Go 测试通过；Portal production build 通过。
- 后端重建部署后完成真实 10 并发 SSE 和 post-release 验证。

## 剩余风险

当前容量为单进程固定上限；多副本必须将服务端流内过载事件与全局供应商预算、租户公平配额和用户优先级结合。浏览器 E2E 还应验证捕获到该结构化 error 后的实际提示与手动重试按钮行为。
