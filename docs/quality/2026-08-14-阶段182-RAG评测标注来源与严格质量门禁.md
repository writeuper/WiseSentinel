# 阶段182：RAG 评测标注来源与严格质量门禁

## 面试缺口

平台已经有 130 条企业场景 Case、关键词/Citation/工具/路由断言和 Recall@K、MRR、nDCG 计算能力，但默认 Case 集没有人工或专家 `relevant_doc_ids` 标注。仅凭 Case 数量不能证明 RAG 召回准确率，工程生成的相关文档猜测也不能直接作为金标准。

## 实现

- 评测 Case 增加三个显式字段：
  - `relevant_doc_ids`
  - `relevance_label_source`
  - `relevance_label_status`
- 支持的已验证来源为 `human`、`expert_review`、`golden_set`，且状态必须是 `verified`。
- 聚合报告同时输出：
  - 普通显式标注样本
  - 仅已验证标注样本
  - `verified / unverified / unlabeled` 标签统计
- 新增 `--require-verified-relevance` 严格门禁。默认要求至少 100 条已验证样本，可通过 `--min-verified-relevance-samples` 调整；门禁失败发生在任何 HTTP/API 请求之前。
- 评测运行元数据记录标注策略和允许的来源，便于比较不同数据集和版本。

## 当前事实

默认 `enterprise_agent_eval_cases_130.csv` 已包含标注字段，但现阶段这些字段为空，因此：

- 行为评测仍可运行并统计路由、工具、关键词、Citation 和延迟；
- RAG Recall@1/3/5、MRR、nDCG 和严格排序指标必须显示 `N/A`；
- 使用 `--require-verified-relevance` 会在调用服务前失败，并明确提示缺少至少 100 条 verified 样本；
- 不把 130 条 Case、关键词命中或 Citation 结构有效率冒充人工召回准确率。

## 标注与发布流程建议

1. 从真实脱敏查询中抽取候选问题，固定知识库 generation、Embedding profile、TopK 和检索策略。
2. 由至少两名具备业务知识的评审者标注相关文档，处理分歧并保留 adjudication 记录。
3. 只把完成复核的行标记为 `relevance_label_status=verified`，来源写入 `human` 或 `expert_review`；模型自动生成的候选只能标记为 `unverified`。
4. 冻结数据集 SHA-256、评测代码 commit 和运行环境，至少积累 100 条有效样本后再对外报告 Recall/MRR/nDCG 及置信区间。

## 验证证据

- 25 条 Python 单测覆盖来源分类、严格过滤、最小样本门禁和生成矩阵字段。
- 默认数据集严格门禁可复现失败，不会产生虚假的 RAG 质量数字。
