# 阶段 175：RAG 排序评测指标实现

## 背景

面试中暴露的核心指标缺口是：已有评测主要验证路由、关键词、工具命中和 Citation 结构，不能直接回答 RAG 的 Recall@K、MRR、nDCG。若没有 relevance 标注，任何“召回准确率”都不可信。

## 实现

扩展 `scripts/run_agent_eval.py`：

- 输入 Case 可增加 `relevant_doc_ids`，用 `|` 分隔人工标注的相关文档 ID；
- Chat 结果自动记录去重后的 `retrieved_doc_ids`（来自服务返回 Citation）；
- 汇总输出 `Recall@1/3/5`、`MRR`、`nDCG@5` 和样本数；
- 没有同时存在标注与检索结果时输出 `sample_count=0` 和 `N/A`，不将关键词命中或 Citation 字段完整性冒充排序质量；
- 每行结果保留检索 ID，便于 Bad Case 复核和文档版本追踪。

## 使用约定

```csv
case_id,...,relevant_doc_ids
RAG-001,...,doc-runbook-a|doc-runbook-b
```

评测结果 CSV 中的 `retrieved_doc_ids` 由 HTTP 响应 Citation 生成。正式评测还应冻结租户、文档 generation、embedding/model 版本和 TopK，并至少积累 100 条人工复核样本后再形成发布结论。

## 验证

- 新增 Recall/MRR/nDCG 单测和无标注拒绝统计单测。
- Python 自动化测试：53/53 通过。
- 既有 Go、race、敏感信息和构建门禁继续作为提交前门禁。

## 可信度边界

本阶段只增加计算能力，没有虚构相关性标注或线上样本；当前仓库的 130 条通用评测集仍未自动获得人工 relevance 标签，因此真实 RAG 排序指标仍为 `N/A`，待冻结标注集后采集。
