# 阶段 67：Ops 工具最小化与评测精确率

日期：2026-08-11

## 缺陷发现

冻结用例 `ROUTE-003`（“当前有哪些 firing 告警需要处理”）初次真实执行虽通过 required-tool 断言，却调用了告警、部署、日志、链路日志、指标和时间等六类额外工具，端到端 23.674s。旧评测只检查“必需工具存在”，没有将无关工具列为 forbidden，因此把低工具选择精确率、额外数据读取和模型/工具成本隐藏为成功。

## 根因与企业级方案

`focusedToolRequests` 没有识别“firing/当前告警盘点”句式，随后进入通用 Plan-Execute 图；该图为兼容部分模型的 tool-choice 问题强制工具调用，导致模型可反复选择无关工具。

企业级 Agent 应把工具选择视为最小权限决策，而不只是完成率：确定性、低风险的意图优先进入受控 allowlist；评测同时统计 required recall 与 forbidden-tool=0 的 precision/overreach。复杂意图才允许在预算内使用通用 Agent 图。

## 落地

- 将 firing/当前告警盘点映射为只读的 `query_prometheus_alerts` focused 工具集。
- 将六个不相关工具写入 `ROUTE-003.forbidden_tools`，使未来过度调用会导致评测失败。
- 新增 Ops 单元测试，固定断言该意图只产生一个告警工具请求。

## 回归证据

```bash
go test ./internal/agent/ops -count=1 -v
python3 scripts/run_agent_eval.py ... --case ROUTE-003
```

真实回归：route=ops、required tool 1/1、forbidden tool 0/6、关键词 2/2、HTTP 端到端 427ms。持久任务指标为 run/e2e 0.651s、queue 0。安全响应仍只展示受控证据投影，未读取或输出工具正文。

## 影响与后续

该变更减少不必要的只读上游调用、成本和潜在敏感读取面，但只覆盖确定性告警盘点意图。其他复杂诊断的工具预算、工具选择 precision、每工具调用上限和最终可靠性仍应在扩展评测集中分别测量；不得为了提高通过率删除 forbidden 断言。
