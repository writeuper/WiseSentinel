# 阶段 133：工具耗时分层与快速调用精度修复

## 发现

平台原先将工具耗时通过 `time.Since(...).Milliseconds()` 直接截断。大量本地日志、指标和部署查询在 1ms 内完成，持久化为 `0ms`，导致工具 P50/P95 无法区分真实快速调用，也会掩盖小幅性能回归。

## 修复

- Tool Gateway 对已执行调用设置最小 `1ms` 记录值；
- 保持现有 `latency_ms` 字段和接口兼容，不伪造亚毫秒精度；
- 新增 Gateway 测试，确保成功执行的工具耗时不再为 0；
- 质量报告新增按工具分层的调用数、成功率、均值、P50、P95 和成功调用 P95；
- 报告只输出工具名称和聚合数值，不输出参数、返回体、Trace、租户或敏感内容。

## 修复前基线（历史持久化样本）

历史数据中部分工具出现 0ms：

- `query_internal_docs`：P50 168ms，P95 392ms；
- `mcp_time_convert_time`：P50 2ms，P95 1,658ms；
- 本地 `search_logs`、`query_metric_range`、`query_prometheus_alerts` 等存在大量 0ms 样本。

这些历史 0ms 样本不能回写修复，只能作为旧口径基线。新调用会至少记录 1ms，后续窗口的工具分位数更可信。
