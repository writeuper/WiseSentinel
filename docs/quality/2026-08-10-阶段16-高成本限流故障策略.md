# 阶段 16：高成本限流故障策略

## 根因

阶段 15 的 Redis 滑动窗口在 Redis 执行出错时一律 fail-open。Chat、Ops 和签名 Webhook 均可能触发模型、RAG、外部工具和异步任务；当限流依赖失效时继续放行会把基础设施故障放大为成本失控和级联过载。

## 企业级方案与取舍

对高成本、可重试的入口选择 fail-closed：Redis 限流不可用时返回稳定 503，让调用方退避重试；对将来低成本、只读或有本地保护的入口可显式定义不同策略，而不是隐式继承。代价是 Redis 故障时可用性下降，因此生产需要 Redis HA、监控与容量演练。

## 落地

- 新增 `ErrRateLimitUnavailable`（50302）。
- `rateLimitFailsClosed` 明确列出 Chat、Ops、Webhook 三个高成本配额类别。
- Redis EVAL 出错时上述入口返回 503；未声明类别不自动继承 fail-closed。
- 新增单元测试，验证每个高成本类别及未知类别的故障策略。

## 回归证据

```text
go test ./internal/pkg/apperr ./internal/gateway/middleware
make verify
```

均通过。

## 遗留项

- 目前尚无 Redis 不可用的真实 HTTP 集成测试；需要验证请求不会进入 Chat/Ops/handler，且客户端获得 50302。
- 需要为 Redis 限流添加可用性、拒绝率、EVAL 延迟和 fail-closed 计数指标，并建立告警/演练。
- 多 Redis 分片、区域故障和本地限流 fallback 的策略需随生产部署拓扑进一步设计。
