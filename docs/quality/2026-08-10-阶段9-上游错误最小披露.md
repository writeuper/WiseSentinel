# 阶段 9：上游错误最小披露

## 根因

模型、Prometheus、MCP 日志和部署 API 适配器会在 HTTP 失败时读取并拼接完整响应 body。即使阶段 8 在最终 HTTP 响应处再次脱敏，原始 body 已进入错误链，仍可能被重试、日志、Trace 或新的调用点泄露。

## 企业级方案

失败响应遵循最小披露：错误只保留 provider、HTTP status 和可选 request ID；不读取失败 body。成功响应仍按既有 schema 读取与解析，不改变工具业务结果。request ID 也作为诊断字段经过安全摘要后再传播。

## 落地

- `OpenAIEinoModel` 在读取 body 前判定失败状态，非流式和流式均返回 `LLM HTTP <status> [request_id=...]`。
- 新增 adapter 级 `upstreamHTTPError`，统一 MCP、Prometheus、部署 API 的安全错误格式。
- `query_logs`、`query_logs_by_trace`、`query_deployments`、`query_prometheus_alerts`、`query_metric_range` 在失败时不再读取 body。
- Prometheus `status:error` 不再回显 provider 的 `error` 字段。
- 更新 Prometheus 回归断言，验证 provider 错误文本不会再出现在错误信息中。

## 回归证据

```text
go test ./internal/model ./internal/toolkit/adapters
make verify
```

均通过。

## 遗留项

- 网络错误（例如代理返回的错误字符串）仍由 Go transport 提供；阶段 8 的统一出口和脱敏组件作为第二道防线，后续可将其归一成连接/超时/DNS 类别。
- DashScope embedding、其他非 HTTP 工具和 MCP stdio 响应限额尚需继续做同样治理。
- 应在隔离集成环境中以带 canary 的上游 4xx/5xx 验证响应、日志、Trace、数据库均为零明文。
