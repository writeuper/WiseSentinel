# 阶段 137：Agent 延迟与指标可信度

## 本阶段修复

质量聚合脚本此前把全部 finished Trace 的数量直接作为 `traces_with_steps`，会把没有持久化 Step 的早期失败/准入终态误报为“有执行步骤”。本阶段改为分别输出：

- `finished_traces`：所有已完成 Trace；
- `traces_with_steps`：至少存在一个持久化 Step 的 Trace；
- `avg_per_trace`：以全部 finished Trace 为分母的平均步数；
- Agent 成功、业务终态、全部终态的 P50/P95；
- 工具历史记录中的 `zero_latency_samples` / `zero_latency_rate`，用于识别旧版本毫秒截断造成的质量风险。

## 真实场景验证

在隔离会话中执行 `CHAT-001`（RAG 问答）和 `CHAT-002`（当前时间工具）并自动删除测试会话：

- CHAT-001：1/1 通过，端到端耗时约 19.2s；产生 2 次 RAG 检索和 2 次模型调用；
- CHAT-002：1/1 通过，端到端耗时约 154ms，工具命中与关键词断言均通过；
- readiness：`ready=true`，依赖组件均为 up；
- RAG：成功样本 2，均值约 611ms，P95 为 1000ms histogram bucket upper bound；样本少于 30，仅作开发验证，不作为生产 SLA；
- 模型：成功样本 2，均值约 8726ms，P95 为 20000ms histogram bucket upper bound；
- Agent 持久化 Trace（运行样本合并后）：成功 Trace P95 约 27.7s，业务终态 P95 约 30.0s，全部 finished P95 约 30.0s，平均步数约 2.927。

## 历史数据质量说明

当前工具调用表中仍有较高比例的 0ms 样本，例如 `search_logs` 约 97%、`query_metric_range` 约 96%。这些记录来自旧版本的 `time.Duration.Milliseconds()` 截断，不能解释为真实零耗时。Tool Gateway 已对实际执行增加至少 1ms 的持久化下限；报告现在显式展示零值比例，便于后续按部署版本切分基线。

## 结论与后续门禁

当前可可信报告的口径应优先使用：

1. 持久化 Trace 的业务终态 P50/P95；
2. RAG/模型直方图的成功样本 P95，并标注 bucket upper bound 与样本量；
3. 工具成功率与零值质量信号结合解读；
4. `abandoned` 单独作为恢复可观测性状态，不计入业务失败率。

生产发布前应累积至少 30 个成功 RAG/模型样本，并按版本切分旧工具记录，避免历史截断数据污染新版本 SLO。
