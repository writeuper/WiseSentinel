# 阶段 47：RAG 评测语料传输完整性与蓝绿重建

## 问题与影响

真实 HTTP 冻结评测首次达到 22/24 后，`CHAT-001` 与 `RAG-001` 仍未命中指定的订单服务文档。文档记录、索引任务和租户权限均正常；不能通过降低置信阈值、移除 generation 过滤或修改评测期望来让用例通过。

根因是历史批量脚本 `scripts/upload_rag_docs.py` 使用 `email.mime.MIMEApplication` 创建 HTTP multipart 文件部分。该类默认生成 `Content-Transfer-Encoding: base64`；脚本把 MIME body 原样发送，服务端正确地按上传字节持久化，因此 Markdown 正文被以 Base64 文本写入并嵌入。查询中的中文、`order-service`、`mysql deadlock` 等词项无法与该 Base64 内容匹配，低置信 RAG 路径不返回 citation。

影响范围是由该旧脚本导入的评测语料；在线上传 API、租户/密级过滤、generation read fence 和模型 API 不应为此放宽。

## 方案与取舍

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 降低 RAG 置信阈值 | 拒绝 | 会把无关或损坏内容作为“内部知识证据”返回。 |
| 服务端自动识别并解码 Base64 | 拒绝 | Base64 是合法文本，静默变换会破坏用户原文、审计和可复现性。 |
| 直接删除旧向量再写新向量 | 拒绝 | 出现嵌入/写入失败时会造成可用知识空洞。 |
| 修复上传 wire body + 蓝绿替换受控文档 | 采用 | 新文档先完成异步索引和 citation 验证；旧文档仅在新版本可读后软删除，物理向量由既有 GC 处理。 |
| 提供 generation-fenced reindex API | 采用 | 文档内容未变而嵌入模型或索引配置变化时，可在不删除现有可读 generation 的情况下异步重建。 |

## 落地实现

1. `build_multipart_upload` 直接构造 binary-safe HTTP multipart 文件部分，保留原始 Markdown bytes，不再生成 MIME transfer encoding；新增 `--include` 支持定向补数。
2. `scripts/test_upload_rag_docs.py` 覆盖 UTF-8 Markdown 原字节、字段和值、无 `Content-Transfer-Encoding` 的 wire 合约。
3. 新增 `POST /api/v1/knowledge/documents/{doc_id}/reindex`。该端点仅接受本租户 active 文档，复用 `SubmitIndexTask` 和已有 generation 分配、lease、发布 CAS 与 GC 机制；请求路径不删除旧向量。
4. Portal 知识库列表增加“重建索引”受控操作，明确旧版本会保持可读直到新版本发布。
5. Portal Chat 在 RAG 开启但没有 citation 时明确提示“未提供可验证的知识库引用”；有 citation 时显示实际资料数量，避免把模型回答伪装为知识库事实。

## 后续门禁与剩余风险

- 评测上传脚本不得再使用会转码文件正文的 MIME builder；每次更换客户端库均须运行字节级 wire regression。
- 已有历史文档须走“发现候选编码异常 → 人工批准 → 新文档/新 generation 建立 → citation 验证 → 软删除旧版本”流程；禁止生产环境自动解码或无验证批量删除。
- 24 条是冻结冒烟集，不等同于生产语料质量。上线前继续建设按租户、密级、文档版本、语言和业务服务分层的 100+ 人工标注样本，并报告 Recall@K、MRR、nDCG、citation 可信度、泄漏率和 P95。
- 当 generation churn 很高时，后过滤的候选窗口仍可能影响召回；后续按架构评审引入受上限的自适应 candidate widening，同时保持 tenant、ACL 和 active-generation fail-closed 过滤。
