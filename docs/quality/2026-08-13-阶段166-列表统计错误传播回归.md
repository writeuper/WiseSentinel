# 阶段 166：列表统计错误传播回归

## 发现

Approval 和 OpsTask 列表查询在分页数据 `Scan` 成功、后续 `COUNT` 失败时，原实现返回部分 rows、`total=0` 和 `nil error`。上层 Handler 会将其序列化成成功响应，造成管理面分页总数错误，且 HTTP/质量指标无法识别数据库故障。

## 修复

- `ApprovalRepo.ListPending`：COUNT 失败时返回原始错误。
- `OpsTaskRepo.ListByTenant`：COUNT 失败时返回原始错误。
- `OpsTaskRepo.ListByTenantAndCreator`：COUNT 失败时返回原始错误。

这保持了现有 API 错误投影和审计链路，避免把部分数据误报成完整成功结果。Document、FaultKnowledge、Session 列表此前已正确传播 COUNT 错误。

## 验证

- `go test ./...`：通过。
- `go vet ./...`：通过。
- Repository/Handler race 测试：通过。
- Python 自动化测试 50 项：通过。
- 敏感信息静态检查：通过。

## 影响

数据库统计查询故障现在会进入统一 5xx/内部错误路径，调用方可以重试或告警；不会再产生 `items` 与 `total` 不一致的假成功响应。
