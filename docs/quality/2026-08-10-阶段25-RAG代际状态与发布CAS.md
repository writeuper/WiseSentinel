# 阶段 25：RAG 代际状态与发布 CAS

## 根因

Index Worker 的 `execution_token` 只能围栏 `ws_index_task` 终态；Milvus 写入没有对应的可发布版本。旧任务在新任务提交后仍可能完成，且现有 delete-then-insert 流程不能判定哪一批向量可被读取。缺少耐久的 generation 指针，无法把“已写入”与“已发布”分离。

## 企业级方案与取舍

采用 MySQL 作为发布权威、Milvus 作为 staged 向量存储：

1. 每个 `(tenant_id, doc_id)` 维护单独的 `next_generation`、`desired_generation` 和 `active_generation`。
2. 提交任务时，在一个事务中锁定状态行、递增 generation、推进 `desired_generation` 并创建 pending task。
3. 未来 Worker 写入 generation 的向量后，只有任务仍为 running、execution token 匹配、文档仍 active 且 `desired_generation` 未推进时，才能在同一事务切换 `active_generation` 与任务成功态。

未选择用 Redis 锁或 Milvus metadata 单独裁决发布：Redis lease 不能提供跨进程持久化一致性，Milvus 也不能与任务状态做原子事务。未把 active generation 直接放入 `ws_document`，以免索引运行状态耦合业务文档生命周期；专用状态表更易于回填、观测和独立演进。

## 落地

- 新增 `ws_document_index_state`，保存 next/desired/active generation、active task、legacy 兼容标记和发布时间。
- `ws_index_task` 新增无符号 `generation` 与 `(tenant_id, doc_id, generation)` 唯一索引。
- 新增可重复运行的 migration `20260810_document_index_generation.sql`：通过 `information_schema` 驱动条件 DDL，兼容当前 MySQL 对 `ADD COLUMN IF NOT EXISTS` 语法的差异。
- `DocumentIndexStateRepo.AllocateAndCreateTask` 使用 `SELECT ... FOR UPDATE` 将 generation 分配和任务创建放入一个事务。
- `DocumentIndexStateRepo.PublishIfOwned` 以 task token、desired generation 和文档 `active` 状态进行发布 CAS，并在同一事务更新 active 指针和任务成功态。
- `RAGService.SubmitIndexTask` 已接入原子分配入口；所有新增任务都有 generation。

## 自动化回归与缺陷闭环

先新增真实 MySQL 集成测试，初始因 repository 与 generation 字段缺失而编译失败；实现后验证：

- G1 分配为 1、G2 分配为 2。
- 已领取 G1 在 G2 提交后，即使 token 正确也不能发布。
- G2 持有正确 token 时可发布，且 active pointer、legacy 标记、任务终态、chunk count 同步更新。
- migration 连续执行两次均成功，验证其可重复性。
- 原 Index Worker lease/CAS 集成测试仍通过。

## 遗留项与下一阶段门禁

- 当前 Pipeline 尚未将 `task.generation` 写入 Milvus metadata，仍会 delete-then-insert；因此 `PublishIfOwned` 尚未接入实际 Index Worker 成功路径，不能宣称已完成端到端 generation fencing。
- 下一阶段必须写入确定性 chunk ID、`generation`/`task_id` metadata，移除索引路径的预删除，并以 `PublishIfOwned` 替换直接 `MarkFinishedIfOwned` 成功路径。
- 读路径随后必须仅接受 active generation（兼容 legacy generation 0），并提供受限候选扩展、全租户批量 resolver 与 generation GC。
