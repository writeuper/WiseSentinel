# 阶段 131：Agent 全量评测与 MCP 时间回退修复

## 目标

在真实 HTTP、RAG、工具和限流环境下复核 Agent 平台整体效果，区分业务断言失败、模型长尾和测试身份触发的容量拒绝，并修复已确认的工具降级缺陷。

## 发现与修复

### MCP 时间工具降级

全量评测中 `TIME-002`、`TIME-006`、`TIME-010` 稳定返回 HTTP 500，错误为 MCP `convert_time` 工具返回错误。根因是 MCP 初始化成功但单次工具调用失败时，`SetMCPTimeAdapter` 直接覆盖了本地确定性 adapter，调用错误未继续 fallback。

修复后：

- MCP 仍作为首选实现；
- MCP 调用失败自动回退本地时区转换实现；
- 新增 Gateway 回归测试，验证 MCP `IsError` 时仍返回正确 UTC/美国东部结果；
- `TIME-002`：通过，153 ms；
- `TIME-006`：通过，149 ms；
- `TIME-010`：通过，401 ms。

### Agent 步数指标口径

质量聚合脚本原先只从 `ws_agent_trace_step` 统计步数，可能漏掉已完成但零步骤的早期失败 Trace，也可能混入未完成 Trace。现改为所有 `finished_at IS NOT NULL` 的 Trace 左连接 Step，并按 `trace_id + tenant_id` 关联。当前报告的平均步数分母覆盖全部已完成 Trace。

## 真实评测证据

### 130 条未限速全量评测

使用 130 条企业评测集、真实 HTTP、会话创建/清理和 Trace 校验执行：

- 通过 99/130，表面通过率 76.2%；
- 25 条为 `42901 rate_limited`，集中发生于连续 Ops 请求触发 30/min 用户限流；
- 3 条模型服务超时；
- 3 条时间工具 HTTP 500（已修复）；
- P50 998 ms，P95 27,934 ms。

该结果不能直接作为 Agent 业务准确率，因为平台限流拒绝与诊断断言失败混在一起。

### 受控速率 Ops 评测

以 2.1 秒请求间隔（低于 30/min 限流阈值）重跑全部 85 条 Ops Case：

- 通过率：85/85（100%）；
- 路由准确率：100%；
- 工具命中/成功：114/114（100%）；
- 关键词命中：327/330（99.09%）；
- P50：2,099 ms；P95：2,141 ms；
- 无 rate limit、timeout 或 HTTP error。

这证明原始全量评测中的 Ops 失败主要是评测速率超过平台保护策略，而不是 Ops Agent 诊断逻辑失败。

### Chat/RAG 长尾

受控 Chat/RAG 执行过程中，已完成的前 34 条中 33 条通过，1 条 `RAG-010` 首次超时；单独重试后通过，路由、工具、关键词和 Citation 均通过，但耗时 42,462 ms。说明当前主要剩余风险是模型/多步链路长尾，不应把重试后的通过率等同于首请求 SLA。

## 剩余风险与建议

1. 生产评测应按平台限流预算分批或使用独立评测身份，并单独报告 `rate_limited`、`timeout`、`http_error` 和业务断言失败。
2. 需要继续优化模型调用预算、Prompt/多步规划和超时重试，重点关注 RAG 多步任务的 30–60 秒长尾。
3. RAG P95 应由 Prometheus 持久化 recording rule 按窗口聚合；不能跨平台进程重启直接相加内存样本。
