# 阶段 12：前端受控路由守卫

## 根因

Portal 侧边栏会根据角色隐藏 Ops、审批和管理入口，但直接输入 URL 仍会挂载相应页面。后端 RBAC/ABAC 是最终安全边界，但这种 UI 行为会造成误导、无效请求和敏感运营页面短暂加载风险。

## 企业级方案

采用服务端授权为权威、前端角色守卫为防御纵深的双层模式。前端复用 API 定义的 `Role` 类型，避免权限列表退化为任意字符串；无权限用户获得明确的 403 反馈而不是隐式跳转。

## 落地与缺陷修复

- 新增 `RoleRoute`，未认证用户跳转登录；具备任一允许角色才挂载受控页面，否则展示 403 与返回对话操作。
- Ops 要求 `operator|sre_admin|platform_admin`；审批和管理要求 `sre_admin|platform_admin`。
- 首次类型检查发现 `string[]` 与 AuthContext `Role[]` 不兼容；改为复用 `api/types` 的 `Role` 类型，确保前后端权限枚举一致。

## 回归证据

```text
make typecheck-frontend
make verify
```

均通过；`make verify` 同时运行 Go 全量 short tests 和敏感 sink 静态门禁。

## 遗留项

- 前端守卫不能代替 API 授权，后端 RBAC/ABAC 必须继续作为唯一权威。
- 当前没有 React Router/RTL 交互测试；后续需断言 viewer 直达 `/ops`、`/approvals`、`/admin` 时不挂载受控内容，允许角色可正常进入。
- AuthContext 在 `/me` 刷新失败时保留缓存角色；后续应在 token 失效/身份不确定时收敛到最小权限并引导重新登录。
