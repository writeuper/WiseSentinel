# 阶段 26：RAG 代际写入与读侧过滤

## 根因

阶段 25 虽建立了 generation 发布状态，但旧 Pipeline 仍会在写入前删除现有向量，chunk ID 由随机值生成，Milvus metadata 也没有 generation。即使 MySQL CAS 已存在，重试写入仍可能重复，未发布/已淘汰向量也可能被检索结果直接返回。

## 企业级方案

索引流程采用“staging write → durable publish → read-side authorization”三段式：

- 每个 chunk 的主键由 tenant、document、generation、chunk index 和内容哈希确定；重试采用 Milvus Upsert。
- Pipeline 不再删除旧 generation，只写入新 generation 与 task identity。
- Worker 写入/flush 完毕后执行阶段 25 的 `PublishIfOwned`；失去 token、被更高 generation 淘汰或文档已删除时不能发布，并将自身任务标记失败（若仍持有 token）。
- Retriever 先用 Milvus 执行 tenant/ACL 候选查询，再用 MySQL active-generation 状态过滤；无 state 的 legacy 文档只允许无 generation/0 generation 向量，带 generation 的未知或 staged 向量一律拒绝。

将 generation 仅作为 Milvus expression 条件不可行：全租户检索无法与每个 document 的 MySQL active generation 做动态 join。当前实现采用受上限的候选扩大后过滤；候选不足时宁可降低召回，不返回未验证向量。

## 落地

- `IndexTaskRequest`、`ChunkInput` 和 Eino 索引上下文传递 task ID 与 generation。
- 新增 `DeterministicChunkID`；相同输入稳定，相异 tenant/doc/generation/chunk/content 必定隔离。
- Milvus metadata 新增 `generation` 和 `index_task_id`；索引写入从 `Insert` 改为 `Upsert`。
- 移除 Pipeline 的 source/doc 预删除；缺少 task ID 或 generation 时显式拒绝。
- `RAGService.ExecuteIndexTask` 以 `PublishIfOwned` 替代直接成功态写入。
- `MilvusRetriever` 接入 `ActiveGenerationResolver`，通过 MySQL 状态 fail-closed 过滤候选；已发布 generation 才返回。
- 更新现有 Pipeline Milvus 集成测试，重索引请求明确使用 G1/G2。

## 自动化回归

先新增确定性 ID 与 generation 读侧过滤测试；在实现前分别因函数/类型缺失而失败。实现后覆盖：

- 同输入 ID 相同；tenant、doc、generation、chunk index、内容任一改变均产生不同 ID。
- legacy 无 generation 结果可见；已发布 generation 精确匹配可见；旧 generation、staged generation 和未知状态的带 generation 结果均被拒绝。
- Generation state 的 MySQL 发布竞争测试持续通过。

首次执行 `go test -tags=integration ./internal/rag` 时，Milvus 已停止且测试按既有约定跳过；诊断显示 `milvus-standalone` 因 etcd 协调超时退出。仅启动本地 compose 的 Milvus 服务（不清除任何卷）后，RAG 测试又暴露了两个真实缺陷：集成测试包未导入 MySQL driver/配置隔离 DSN，且旧重建用例直接调用 Pipeline、绕过 durable task 与 publish 状态。

已修复测试基础设施并将重建用例升级为真实的“创建文档 → Submit → Claim → Execute → Publish → Retrieve → Reindex”链路。恢复后的 MySQL + Milvus 回归全部通过：检索循环、G1→G2 重建（结果仅为 G2）、租户隔离和密级过滤。

## 遗留项

- 仍需新增故障注入测试：未发布 G、G1/G2 乱序、Worker 崩溃后 Upsert 重试和跨租户删除隔离。
- Resolver 当前候选扩展上限为 100，尚未实现自适应分页、drop ratio 指标、告警与容量压测。
- 删除文档仍是同步向量删除后软删除；应改为 durable deletion 先胜出、读侧立即拒绝、异步 generation GC 可重试的协议。
