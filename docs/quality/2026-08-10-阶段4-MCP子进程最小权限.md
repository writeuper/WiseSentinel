# 阶段 4：MCP 子进程最小权限

- 日期：2026-08-10
- 状态：已完成 P0 环境隔离、命令/参数白名单与回归
- 协作角色：Agent 架构师、安全工程师、自动化测试工程师

## 1. 问题与影响

MCP stdio client 原先将 `os.Environ()` 传给 MCP SDK。更严重的是 SDK 默认启动逻辑会再次合并父进程环境，因此 MCP 子进程可读取 JWT、LLM/Embedding API Key、数据库/Redis/Milvus 密码和部署令牌。启动命令及参数也完全来自配置，没有绝对路径或精确参数校验。

这会使一个被篡改、被替换或具有恶意行为的 MCP server 获得平台级密钥，突破 Agent 工具边界。

## 2. 企业级方案

MCP server 被视为不可信外部执行边界，采用最小权限启动 profile：

- 命令必须为绝对路径并命中 allowlist；参数必须与批准 profile 精确一致。
- 子进程环境采用 replace 而非 merge，仅显式传递运行所需的 `PATH`、`HOME`、区域/时区和证书/缓存路径。
- 不继承任何业务密钥。生产仍应使用独立低权限运行身份、只读文件系统、无 Docker socket、网络默认拒绝，以及镜像/二进制 digest 固定。

## 3. 落地实现

- 新增 `StartOptions`，支持命令、参数和环境 allowlist。
- 使用 MCP SDK 的 `WithCommandFunc` 自行创建 `exec.Cmd`，并直接设置 `cmd.Env`。这消除了 SDK 默认 `append(os.Environ(), ...)` 的隐式继承。
- Bootstrap 从 `mcp.time` profile 读取允许的命令、精确参数和环境键。
- 更新 time MCP 配置，显式声明批准 profile。
- 新增测试：拒绝相对路径、拒绝未允许命令/参数、验证敏感父环境不会进入子进程命令环境。

## 5. 遗留风险与下一步

- 当前 `uvx` profile 仍会在运行时解析 Python 包；生产应改为镜像内预装、版本和 artifact digest 固定的 MCP launcher。
- 未实现 MCP `serverInfo`、tools/list 集合及 schema 指纹校验；对端能力偏差应 fail-closed。
- stderr 尚未设置受限异步 drain，响应大小/内容数量及独立熔断/资源配额也待补充。
- 工具调用原文仍存在日志和持久化脱敏不足的问题，应建设统一字段级脱敏与完整 allow/deny/approval 审计。
