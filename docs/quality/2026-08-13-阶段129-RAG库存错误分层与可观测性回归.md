# 阶段 129：RAG 库存错误分层与可观测性回归

## 发现

`ws_rag_inventory_refresh_errors_total` 原先是无标签单计数，只能知道刷新失败，不能区分 MySQL/逻辑库存查询失败和 Milvus/物理向量统计失败。企业级排障无法据此判断是元数据数据库问题还是向量数据库问题。

## 修复

- 指标改为 `ws_rag_inventory_refresh_errors_total{stage="logical|physical"}`；
- `logical` 对应 ActiveRAGInventory 数据库查询；
- `physical` 对应 Milvus PhysicalVectorCount；
- 未知 stage 归一为 `logical`，避免任意标签注入；
- 保留原有 gauge 语义：刷新失败时不把旧值伪装成新值，也不把 logical chunks 冒充 physical vectors。

## 验证

- 新增观测层测试，验证 logical/physical 两个固定标签和未知值归一；
- Go 观测、Bootstrap 测试通过；
- 重建并启动新平台二进制，readiness 全部组件 `up`；
- Milvus 自动重连指标仍保持低基数 `success/failure`；
- Compose、Python、Bundle、敏感信息门禁全部通过。

## 指标口径注意

本次平台重启后，Prometheus 进程内计数器重新从零开始。旧生命周期的无标签 `ws_rag_inventory_refresh_errors_total=5` 不应与新生命周期的分 stage 数据相加；生产应依赖 Prometheus 持久化抓取和 recording rules 做跨重启聚合。

## 当前运行态

- `/health/ready`：全部组件 `up`；
- Milvus：running/healthy；
- RAG 逻辑库存：24 个 active documents、78 个 published chunks、11 个 legacy documents；
- 物理向量：198；该值包含 legacy、superseded 和 pending-GC rows，不等同逻辑 chunks；
- 当前无新的生产流量证据，以上为本地/集成环境。

## 剩余风险

1. 仍需在专用故障注入环境分别模拟 MySQL 和 Milvus 统计失败，验证 stage 计数在真实失败路径中准确递增。
2. Prometheus counter 跨进程生命周期的持久化聚合尚未在本地环境建立生产级 recording rule。
3. Milvus wrapper reconnect 指标表示 SDK wrapper 主动尝试，不代表所有容器恢复事件。
