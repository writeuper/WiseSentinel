# 阶段 49：Ops 响应证据最小化与审批状态机风险

日期：2026-08-11

## 问题发现

跨角色审计发现同步 `POST /ops/analyze` 仍将运行时 `Evidence.input/output` 和 Agent 自由文本 `result/detail` 返回给浏览器。此前的 `redact.Summary` 只处理已知凭据模式，无法阻止日志、RAG 片段和工具响应中的普通自由文本泄露；Portal 又以 `<pre>` 原样渲染这些字段。

这与阶段 48 的持久化安全投影不一致：异步任务记录已受抑制，但同步响应仍是直接旁路。

## 企业级方案与实现

采用“执行平面保留、呈现平面最小化”的 DTO 契约，而非在前端做正则补救：

- `OpsEvidence` 移除 `input/output`，仅返回工具名、状态、耗时、时间、`suppressed=true` 与输入/输出字节数。
- `toOpsEvidence` 与 `toSafeDetails` 在后端 HTTP 最终出口 fail-closed；同步 `result` 改为稳定状态消息，结构化结论是唯一支持的业务说明面。
- Portal 不再接收/渲染正文，改为显示“内容已由服务端抑制”及容量信号。
- 评测脚本不再依赖工具正文或明细：工具正确性使用工具名/状态，语义使用受控结论。

该方案保留排障所需的工具状态、延迟和 trace 关联，同时禁止运营 UI 成为证据正文仓库。若业务确需原始取证，应使用独立 KMS 加密 evidence vault，包含用途绑定、RBAC、审计和留存期。

## 评测影响与质量结论

安全契约切换后运行 24 场景评测：路由 100%，工具 25/25；整体 22/24（91.7%），关键词 57/68（83.8%）。两个失败均来自旧评测直接依赖工具正文：一个要求 Prometheus `source` 正文，另一个从自由文本结果匹配关键词。该下降不是工具失败，不能通过恢复正文使其变绿。

后续应将 source 设计为受 allowlist 的枚举元数据，并补齐所有 Ops 场景的结构化结论覆盖；再恢复语义评测。P95 21.08s 仍受真实模型/RAG 响应影响。

## 下一阶段 P0：审批状态机

架构审计还确认 L2 工具审批目前不是可恢复 workflow：approval 仅关联工具名、批准后不把 Ops task/intention 入队，且普通工具审批缺少职责分离。不得将其描述为“批准后自动执行”。

下一阶段将以 durable `tool_execution_intent` 实现 `awaiting_approval → approved → runnable → running → terminal`，审批与 intent/task 以事务 CAS 绑定，执行端重新授权并用幂等键/围栏 token 防重放；测试需覆盖批准一次执行、重复批准、拒绝/过期、跨租户、SoD、MySQL/Redis 并发和 canary 无泄露。
