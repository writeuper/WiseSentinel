# 阶段180：SSE 首 Token 延迟可观测性

## 背景

流式 Agent 请求的端到端耗时由请求握手、首 Token 等待、后续 Token 生成和流结束组成。仅观察 `stream_handshake` 或 `stream_complete` 无法定位用户看到首个响应前的等待时间，因此补充 TTFT（Time to First Token）指标。

## 实现与口径

- 新增 `ws_model_stream_ttft_seconds` Histogram，按受控的 provider class 记录。
- 计时起点为流响应体读取协程开始处理的时间；首次收到非空文本 delta 或工具调用 delta 时记录一次。
- usage-only chunk、空 choices 和 `[DONE]` 不计为首 Token，避免把供应商的统计尾包误判为用户可见响应。
- 一个流最多记录一个 TTFT；没有真实内容或工具调用的异常/空流不产生样本。
- provider 标签经过归一化，不写入 URL、租户标识、模型名或密钥等高基数/敏感信息。

## 与其他时延指标的区别

| 指标 | 含义 | 适用场景 |
| --- | --- | --- |
| `stream_handshake` | 发起流请求到 HTTP 响应建立 | 连接、网关和上游握手排查 |
| `stream_ttft` | 流读取开始到首个真实内容/工具 delta | 用户首屏体验、模型排队和首 Token 生成排查 |
| `stream_complete` | 流读取开始到流结束 | 完整响应耗时、超时和长尾排查 |

TTFT 不等于完整 Agent 任务耗时，也不等于生产 SLO；生产基线仍需按模型、区域、租户和请求类型分层，并结合真实流量计算 P50/P95/P99。

## 验证

- 单元测试验证 provider 标签受控、负数延迟被忽略。
- SSE 集成测试先发送延迟后的文本 delta，再发送 usage-only chunk 和 `[DONE]`，确认 TTFT 样本被记录且不由 usage 尾包触发。
- 供应商未返回 usage 不影响 TTFT；Token 用量和 TTFT 是相互独立的观测维度。

## 后续建议

1. 在 Prometheus/看板中按 provider class、模型 profile 和请求模式（文本/工具）展示 TTFT 分位数。
2. 结合 Trace ID 关联 `stream_handshake`、TTFT、`stream_complete` 和 Agent step，区分模型排队、首 Token 生成、工具执行及网络传输耗时。
3. 以脱敏的真实流量或稳定回放集建立分层基线后，再设置告警阈值；当前测试结果仅证明指标链路和语义正确，不宣称生产性能达标。
