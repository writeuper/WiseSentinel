# 阶段 62：审批假成功与集成测试配置确定性

日期：2026-08-11

## 触发与根因

架构、后端与前端复审共同确认：通用 `ws_approval` 的历史 `Decide` 能把任意 `tool_invoke` 记录从 `pending` 更新到 `approved`，但该路径没有 durable intent、原始命令保险库、审批/执行绑定、Outbox 或恢复 Worker。Portal 因此可能显示“已批准”，而实际工具既不会恢复，也不具备安全恢复的必要证据。

本轮真实 MySQL 回归还暴露自动化基础设施问题：`.env` 的 `GF_GCFG_PATH` 是相对路径，Go test 执行到包目录后该路径不再指向项目根目录，GoFrame 初始化数据库配置时 panic。这样会让 `make test-real-scenarios` 在干净 Shell 中不可复现。

## 企业级处理方案与取舍

完整方案应使用 `approval + immutable execution intent + encrypted command vault + transactional outbox + fenced resume worker`。批准必须执行职责分离、过期检查、审批与命令 hash 绑定；Worker 用 `execution_id` 做幂等键，并仅允许当前 DB lease/fencing token 写入终态。

该能力目前未实现且没有已配置 L2 执行适配器。直接恢复通用批准会制造安全与审计假象，因此采用 fail-closed 的最小落地：

- 未有专用“决策并恢复执行”事务的审批类型，批准一律返回 `50303`；不得落到通用状态更新。
- 通用仓储层同样拒绝 `approved`，形成 API 之外的第二道防线；仍可记录拒绝决定。
- `vector_gc_redrive` 保留现有专用原子路径：校验非发起人批准、精确 dead target，并在同一事务中重新入队。

## 实现

- `ApprovalDecision` 对未知类型的批准返回 `ErrHighRiskWorkflowUnavailable`，不再仅写 `ws_approval.status=approved`。
- `ApprovalRepo.Decide` 对通用 `approved` fail-closed，防止后续调用方绕过 Controller。
- `Makefile` 的所有真实 MySQL/Redis/RAG 集成入口固定 `GF_GCFG_PATH=$(CURDIR)/manifest/config`，使测试进程在包级工作目录下仍能找到配置。
- 新增真实 MySQL 用例，断言 `tool_invoke` 的通用批准返回 false 且记录仍保持 `pending`；保留拒绝意见的敏感内容脱敏验证。

## 回归证据

```bash
OPS_TEST_MYSQL_DSN=... make test-approval-integration
go test ./internal/repository ./internal/gateway/handler ./internal/toolkit -count=1
```

结果均通过。审批集成覆盖：过期、CAS 并发决策、拒绝意见脱敏、通用批准 fail-closed。相关单元回归覆盖审批类型 allowlist、审批目标投影与 L2 工具不调用适配器。

部署新后端后，真实 HTTP 冒烟 `ROUTE-001` 通过（路由 100%，关键词 2/3，端到端 26.386s）。该单用例未要求工具，因此工具成功率为 N/A；时延仅作为真实模型单点证据，不能替代全量 24 场景的 P50/P95 基线。

## 未完成的上线阻塞项

真实 L2 写工具仍不可上线；必须先实现上述 durable execution 能力，并补充多管理员并发、过期、跨租户、批准后崩溃恢复、重复 Outbox 投递、双 Worker、旧 lease 回写、外部副作用恰好一次和全链路 canary 脱敏测试。当前的 `50303` 是正确的安全降级，不代表已经支持审批后执行。
