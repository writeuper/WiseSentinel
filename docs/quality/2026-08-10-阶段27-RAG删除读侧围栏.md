# 阶段 27：RAG 删除读侧围栏

## 根因

阶段 26 的 active-generation resolver 只读取索引 state，不检查文档生命周期。当 Milvus 删除失败、延迟或与 Worker 并发时，`ws_document.status='deleted'` 的文档仍可能被 resolver 识别为 legacy/active generation，导致已删除知识继续进入 Chat、Citation 或 Trace。

## 企业级方案

文档业务状态是读取授权的最终条件：resolver 必须从 `ws_document` 出发，只解析 tenant 内 `status='active'` 的 document，并左连接 generation state。缺失 resolver 返回项表示未知、跨租户或已删除，读侧一律 fail-closed。删除顺序采用 durable deletion first：先取消 task、写入 document deleted，再尝试外部向量删除；Worker 的发布 CAS 与 resolver 都因此让删除优先于迟到写入。

不能将同步外部删除失败视为可通过客户端重试自行恢复：文档已删除后 API 正确返回 not found，而遗留向量需要 durable GC/outbox 消费者处理。本阶段先关闭读取泄露窗口，下一阶段再建立可重试清理。

## 落地

- `ResolveActiveGenerations` 改为 `ws_document` 与 `ws_document_index_state` 左连接，仅返回 active 文档；未建立 state 的 active 文档显式返回 legacy generation 0 权限。
- Retriever 对 resolver 中缺失的 document 一律丢弃，不再把缺失 state 推断为 legacy。
- `DeleteDocument` 调整为：取消 active task → `SoftDelete` → tenant scoped Milvus 删除。
- 真实 RAG 集成测试的手工 Milvus fixture 全部创建相应 active `ws_document`，测试后精确清理 document/state/vector，避免用无授权业务记录模拟可见数据。
- 新增真实 MySQL 回归，确认 deleted document 不会出现在 active generation 解析结果。

## 遗留项

- `DeleteDocumentChunks` 失败后尚无 durable GC/outbox；当前安全地拒绝读取，但可能留下不可见 staged/old 向量。
- 需要为 generation GC 记录删除目标、重试退避、执行 lease、按 tenant/doc/generation 精确删除、运行指标和死信/人工介入。
- 仍需加入 Delete 与 Publish 的 MySQL 并发竞争、Milvus delete 超时及 Worker 崩溃后的端到端故障注入。
