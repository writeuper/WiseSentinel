# 阶段 92：同步 Chat 幂等执行

日期：2026-08-11

## 根因

Chat 在网络超时、代理重试或用户重复提交时会重复执行模型和工具。阶段 90 的 session 删除围栏只处理迟到写入，不能识别同一逻辑回合。

## 实现范围

本阶段实现同步 `POST /chat` 的持久化幂等第一段：

- 新增 `ws_chat_turn` 和迁移账本条目，以 `(tenant_id, user_id, session_id, idempotency_key)` 唯一化。
- key 必须是 36–128 位 URL-safe opaque 字符；请求 question 与 RAG/tool options 只保存 SHA-256 hash，不保存原始请求正文。
- `INSERT IGNORE` 选出唯一执行所有者，`execution_token` CAS 才能写入成功/失败终态。
- 相同 key + 相同 hash：成功后返回保存的安全 `ChatRes`，不再调用模型或工具。
- 相同 key + 不同 hash，进行中或失败记录：返回 `40901` fail-closed，禁止隐式重放。
- 因模型或 session 保存失败而终止的回合不会被自动执行第二次；调用者必须生成新逻辑意图。

## 真实验证

`make agent-idempotency-contract` 在认证 tenant 中创建精确 session、顺序提交同一 key 两次，并在 finally 删除且验证不可读：

```json
{"model_calls_delta": 1.0, "outcome": "idempotency_replay_success"}
```

同时验证同一 key 但不同 question 返回 `40901`。脚本只输出类别、指标差量和单向响应 hash 前缀，不输出 key、问题、模型回答或 HTTP body。

数据库并发集成测试验证：8 个并发 claim 仅一个创建者；旧 execution token 不能覆盖成功态；同 key 的不同 user 不会共享结果。

## 有意未启用的路径

- Portal 默认 Chat 是 SSE；流式事件序列尚未持久化/安全重放，因此 Portal 和 `/chat/stream` **没有**发送或宣称支持 `Idempotency-Key`。
- 当前成功回放没有 `replayed` API 字段，前端不存在将回放误显示为新执行的风险；该字段会随 SSE replay 统一设计。
- running 记录没有自动 lease reclaim。崩溃后的同 key 仍 fail-closed，用户需显式产生新 key；恢复 worker、session generation 和事件 replay 是下一阶段前置条件。

## 上线门禁

1. migration ledger 与幂等表迁移必须先完成；本地 Compose 已成功执行该迁移。
2. `go test ./...`、repository integration、race、实时合同、安全 sink 和前后端 build 均须通过。
3. 在 SSE event journal / replay、turn retention/GC、generation CAS 完成前，不得将流式或写工具路径描述为“可安全自动重试”。
