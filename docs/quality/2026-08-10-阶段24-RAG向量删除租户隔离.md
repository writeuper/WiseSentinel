# 阶段 24：RAG 向量删除租户隔离

## 根因

Milvus 检索表达式已按 `tenant_id` 过滤，但索引流水线重建和文档删除分别使用仅含 `doc_id`、仅含 `source_uri` 的删除表达式。UUID 作为通常的文档 ID 并不构成授权边界；共享或意外复用 source URI 时，一个租户的重索引/删除可能误删另一租户的向量。

## 企业级方案

将 tenant 作为所有向量破坏性操作的必填服务端参数，并把 `(tenant_id, doc_id)` 或 `(tenant_id, source_uri)` 写入同一个 Milvus delete expression。调用方不得通过无租户重载回退，领域接口也显式传递 tenant，确保编译期强制更新所有调用链。

完整 RAG generation 设计另见本阶段架构审查结论：索引路径仍存在 delete-then-insert 和外部 Milvus 写入未被任务 token 围栏的问题，需通过 staged generation、数据库发布 CAS 与检索 active-generation 过滤解决；本次修复不将该更大问题伪装为已完成。

## 落地

- `DeleteByDocIDExpr` 改为接收 `tenantID, docID`，生成两字段合取表达式。
- `DeleteBySourceExpr` 改为接收 `tenantID, source`，生成两字段合取表达式。
- `MilvusIndexer`、知识索引 Pipeline、RAG Service、领域接口、知识删除 Handler 与测试 stub 全链路显式传递 tenant。
- 更新 Milvus 集成测试的删除调用，以保持真实环境测试也遵循新契约。
- 新增 filter 回归：文档删除与 source 删除表达式必须精确包含 tenant 条件。

## 回归证据

```text
go test ./internal/rag/filter ./internal/rag/indexer ./internal/agent/knowledge ./internal/rag ./internal/orchestrator/router ./internal/gateway/handler
```

通过。`make verify` 亦通过，覆盖 Go 短测试、Portal TypeScript 编译与敏感 sink 静态检查；真实 Milvus 测试仍需在隔离服务可用时执行。

## 遗留项

- 当前 Pipeline 仍在写入新向量前删除旧向量；lease 失效/重试竞争下不能获得端到端一致性。
- 需要新增文档索引 state、task generation、确定性 chunk ID、MySQL 发布 CAS、检索 active-generation resolver 和异步 GC。
- `DeleteDocument` 目前为同步外部删除再软删除；generation 发布版本中应让数据库删除状态先胜出，再由可重试 GC 清理向量。
