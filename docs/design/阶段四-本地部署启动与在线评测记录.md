# 阶段四：本地部署启动与在线评测记录

## 启动与迁移

使用 `scripts/start_local_stack.sh` 可启动 Compose 的迁移、平台和 Prometheus 服务。迁移继续使用现有 checksum ledger 与 MySQL GET_LOCK 围栏；脚本等待 `/health/live`，然后打印 `/health/ready`。本轮 Docker 启动结果：MySQL、Redis、etcd、MinIO、Milvus、Prometheus 和平台容器均启动，迁移容器正常退出，平台 live 探针返回 HTTP 200。

## 健康检查

`/health/ready` 返回 503，唯一失败类别是 `chat_model=down`、`ops_model=down`，根因为 Compose 未注入 `LLM_API_KEY`/`LLM_BASE_URL`，模型配置为空。该状态保持 fail-closed，不能将平台伪装为 ready。数据库、Redis、Milvus、RAG、Worker、日志和 Prometheus 组件均已正常。

## 在线评测证据

- `/api/v1/auth/token`、`/api/v1/ping`、会话创建和消息读取均返回 HTTP 200。
- 修复 GoFrame 路由组中 `/auth/token` 的公共路径匹配；此前评测登录会被认证中间件误拦截。修复后开发账号登录、创建会话和删除会话均返回 HTTP 200，删除后的消息读取返回 HTTP 404，清理闭环成立。
- 130 Case 数据集生成和 coverage 通过结构门禁，断言覆盖率为 100%，但没有 verified RAG Gold。
- `CHAT-001` 在线评测被分类为基础设施失败：`model profile "chat_fast": API key is required`；不计入模型质量。
- 认证回归后使用开发 JWT 重跑 `CHAT-001`：请求已进入平台，但因默认模型配置为空返回 HTTP 500，评测汇总将其归类为 `infrastructure failure/http_error`，业务通过率保持 N/A；这证明评测门禁没有把部署缺陷误报为模型质量。
- 真实 Provider Benchmark、三次重复运行和人工双评尚未执行。

## 本地协议 Smoke

`manifest/docker/mock-llm.py` 是开发环境专用的 OpenAI-compatible mock，仅用于验证 HTTP 协议、工具 Schema 和 `task_complete` 合同，不代表任何真实模型能力，也不得用于生产流量。

```bash
python3 manifest/docker/mock-llm.py &
LLM_API_KEY=local-smoke LLM_BASE_URL=http://host.docker.internal:8081 \
LLM_MODEL=mock-model docker compose -f manifest/docker/docker-compose.yml up -d --force-recreate platform
```
本轮实际验证结果：`/health/ready` 返回 HTTP 200，`chat_model=up`、`ops_model=up`、`prometheus=configured`，其余数据库、Milvus、Redis、RAG 和 Worker 均为 `up`。验证后已恢复无凭据的默认 fail-closed 平台容器，因此当前 `/health/ready` 仍会因真实模型未配置而返回 503。

真实评测必须使用隔离 Provider 凭据、固定 dataset/model/embedding 指纹、双人 Gold 标注和既有 `gate_rag_experiment.py` 发布门槛。
